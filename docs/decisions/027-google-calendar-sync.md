# 027 — Google Calendar sync for coach lessons

**Date:** 2026-10-21
**Status:** Accepted

## Context

The coach keeps lesson appointments in Google Calendar today and copies them in by hand after approving each booking. With more families on the app this doesn't scale, and double-entry creates drift between the lessons table and the coach's working calendar. We want approved lessons to appear automatically in Google Calendar, follow reschedules, and disappear on cancel.

Several constraints shape the design:

- Only the coach connects a calendar — parents never do, and the app is single-coach for the foreseeable future.
- The coach's existing Google Calendar must not be read, scanned, or modified. Only lessons the app itself creates should ever be touched.
- A booking must succeed even when Google is down or the integration is broken. Sync is a side effect, never a gate.
- The refresh token is a long-lived credential to a third-party account and must be protected at rest.

## Decision

**Scope: `calendar.app.created` plus `openid` and `email`.** The only sensitive scope is `calendar.app.created` — on connect, the API creates a dedicated secondary calendar titled "Axiom Aquatics Lessons" and stores only its id. This scope grants access *only* to calendars created by this OAuth client in this session, so there is no way for the app to see or edit the coach's other calendars even if a bug tried. The authorize URL also requests `openid` and `email` — two non-sensitive OpenID Connect scopes we add so Google returns an id_token whose `email` claim populates the "Connected as *email*" line on the status card. Neither widens calendar or data access, and neither requires Google's sensitive-scope review. If the id_token is missing or lacks an email claim (e.g. a workspace account configuration), the connection still succeeds and the card simply shows "Connected" without an address — email is display-only, never load-bearing. Full `calendar` or `calendar.events` would give access to everything the coach can see on their account; we reject those.

**One-way sync, app → Google, via a single reconcile function.** Every lesson route (approve, decline, reschedule, cancel on both coach and parent paths), both batch passes (full and light), and the retry endpoint call the same `syncLessonToGoogle(lessonId)`. The function reads the lesson's current state and makes Google match it. **An event should exist whenever the lesson's status is `approved` or `completed` — upcoming or past, time is never a factor.** Completed lessons stay on the coach's calendar as history after the cron auto-completes them and after any retry that runs post-end-time; deletion is reserved for `declined`, `canceled`, `expired`, `no_show`, or a missing lesson row. (Earlier drafts gated event existence on `starts_at > now()`, which caused the cron and any late retry to erase a day's lessons from Google at midnight — not what the coach wants.) No "created vs updated vs deleted" branching at the call site. The Google event id is the lesson UUID with dashes stripped, so retries and the batch passes are idempotent — an insert that races into a 409 falls through to `events.patch`, and a delete of a never-created id (404/410) is treated as success. Pending lessons do not sync (they may never happen). Nothing in Google ever flows back into the app — if the coach edits an event in Google Calendar, the next app-side change overwrites it. The lessons table is the source of truth.

**Two batch passes, both bounded by a sync window of today-LA onward.** Every batch runs through `runSyncBatch` which sets `sync_run_started_at` before the loop and clears it in `finally`, so a crashed API self-heals via a 2-minute staleness check on the next status read.

- **Full pass** — reconciles every in-window lesson that is `approved` or `completed`, regardless of `calendar_sync_status`, plus any in-window lesson that still carries a `google_calendar_event_id` (so stray events on canceled/declined rows get removed). Sets `last_full_reconcile_at` on success. Triggered by connect, reconnect, and the cron tick when `last_full_reconcile_at` is older than 24 hours — no new cron infrastructure. The full pass is the self-healing mechanism when Google state diverges from the DB (events the coach deleted manually, missed webhooks that don't exist in this architecture, etc.).
- **Light pass** — reconciles up to 50 in-window `approved`/`completed` lessons whose `calendar_sync_status` is `not_synced` or `sync_failed`. Triggered by every cron tick (cheap drain) and by the manual Retry button on the account card. Cap exists so a worst-case retry doesn't burn through Google's user quota in one shot.

The window (`starts_at >= start_of_today_in_LA`) prevents a brand-new or long-disconnected coach from retroactively populating their calendar with months of history they didn't opt in to.

**403 and 429 are retryable; only `invalid_grant` is terminal.** The service treats Google 403 (`rateLimitExceeded`, `userRateLimitExceeded`) and 429 as transient: mark the lesson `sync_failed`, keep the integration `active`, let the next light pass clear it when the quota recovers. Only `invalid_grant` on refresh flips the integration into `needs_reconnect`. This separation matters because quota pushback is common at launch and must not look like token revocation.

**Home-pool addresses are never sent to Google in the event's `location` field.** Lesson locations with a non-null `household_id` are a specific family's private residential address. Pushing that string to a third-party data processor (Google) under the coach's dedicated calendar is a privacy decision we are not ready to make unilaterally — it's pending Jason's input and the kids'-data legal review (see `docs/accounts.md`). Until that review resolves, home-pool events send only `"<name> — <city>, <state>"` to Google; the coach still gets a labeled event with a city-level venue hint but no door-to-door directions. Named pools (public venues; null `household_id`) keep the full address because the "View map" link is a real convenience for the coach and the address isn't private.

**Swimmer first names (never last names) are sent to Google in the event's `summary` field.** The event title is `"Swim lesson: <first>"` or `"Swim lesson: <first> & <first>"` so the coach can distinguish lessons at a glance from the calendar grid. Last names, birth dates, and swimmer ids never leave the app's data boundary — the description carries only a link back to the lesson detail inside the app, and the location follows the home-pool rule above. First names alone are a modest disclosure, but they are information about minors going to a third-party processor and need the same Jason-input + kids'-data legal review as the address decision. Pending that review, we ship first names because the coach's calendar is unusable without a way to tell concurrent lessons apart. If the review requires names to be removed, the summary falls back to generic `"Swim lesson"` and the coach identifies the lesson by clicking through the description link into the app — no code paths outside `buildSummary` and its tests depend on the name string. (Last-name initials — e.g., "Alex R." — were considered as a middle ground that avoids the full-first-name disclosure while still disambiguating siblings. We skipped it for now because single first names already distinguish every lesson Jason has today and adding an initial would require the same legal sign-off as the current approach.) See `docs/accounts.md` kids'-data section.

**OAuth flow lives on the API, not the web app.** The authorize redirect goes to Google, Google calls back to `/integrations/google/callback` on the API, the API exchanges the code for tokens, encrypts the refresh token, and redirects the browser to `/account` on the web app. The callback is pre-registered in Google Cloud as `http://localhost:3001/integrations/google/callback` (dev — matches the API's default `PORT`) and `https://api-dev-9f6d.up.railway.app/integrations/google/callback` (deployed). Since `apps/api/src/app.ts` has no global route prefix, the router mounts directly at `/integrations`. The `state` parameter is an HMAC-signed, 10-minute-TTL token bound to the coach's profile id to prevent CSRF and cross-coach account hijack.

**Refresh token encrypted at rest with AES-256-GCM.** Access tokens live only in memory. The refresh token is encrypted with a 32-byte key supplied via `GOOGLE_TOKEN_ENCRYPTION_KEY` and stored alongside its IV, auth tag, and a `key_version` integer so we can rotate later without a schema change. The web app never sees the token: the connection card calls API endpoints that return status metadata (email, last sync, failed count, status enum), nothing cryptographic.

**Sync failures are isolated from booking writes.** The approve/reschedule/cancel/decline route handlers commit their database change in a transaction, then enqueue the sync as a fire-and-forget call after `res.json()` returns. If the Google call fails, the lesson row's `calendar_sync_status` is updated to `sync_failed` and `calendar_sync_error` captures the message, but the booking is already committed. The coach retries from the UI. No sync code runs inside a lesson transaction.

**Revoked token → `needs_reconnect`, not disconnect.** When `oauth2Client.refreshAccessToken()` returns `invalid_grant` (coach revoked access out-of-band in their Google account), the integration row is **not** deleted. Instead, `coach_calendar_integrations.status` flips to `'needs_reconnect'` and `needs_reconnect_since` is set in the same transaction as the lesson row's `sync_failed` write. All sync hooks short-circuit while in that state (no further Google calls), the retry endpoints return `409 { error: "Reconnection required" }`, and the card shows a Reconnect action. Reconnect reuses `/integrations/google/start`; the callback checks whether the dedicated calendar still exists in Google (`calendars.get`) and either reuses the existing id or creates a new calendar if the coach deleted it. Reason: preserves user intent, settings, and the calendar id across a token revoke.

**Full sync passes run in the background from the callback and from the cron tick.** The OAuth callback redirects to the web app before any sync happens, and a plain `async` function iterates the window and reconciles each lesson sequentially with a 100ms gap. The cron tick runs a light pass every invocation and promotes to a full pass when `last_full_reconcile_at` is >24h old — the same cron that already handles pending-expiry and auto-complete, so no new worker is added. The card polls `/coach/calendar/status` to display "Syncing N of M…" and stops when `syncRunInProgress` goes false (either the run finished or the 2-minute staleness window elapsed and the row is considered idle). No queue or message bus — this matches the rest of the codebase.

**New general `coach_audit_log` table.** Connect, disconnect, and reconnect each write an immutable row inside the same transaction as the state change — same rule the household audit log already follows. The table matches `household_audit_log`'s shape and conventions minus `household_id` plus `coach_id`, deliberately kept generic so other coach-level events can land in it without a new table. The existing `household_audit_log` can't carry these events: its `household_id` is NOT NULL and connect/disconnect/reconnect are coach-level actions with no natural household (a single coach serves many households, and the integration is one-per-coach, not one-per-household). The "needs_reconnect" state transition is detected by the system, not performed by the coach, so it does **not** write an audit row — the integration row's `needs_reconnect_since` is sufficient.

**Exception: `calendar_sync_retried` audits land AFTER the retry loop, not inside it.** The bulk-retry endpoint reconciles every `sync_failed` lesson sequentially, each per-lesson sync wrapping its own transaction around the lesson/integration row writes. The whole batch spans many Google HTTP calls, and no DB transaction can be held open across those calls without hurting the Postgres pool and still not providing durability (Google is the slow side). So the retry audit row writes once at the end with a jsonb `payload` of `{attempted, succeeded, failed}`. Migration 0048 adds the `payload jsonb` column; the audit otherwise matches `household_audit_log`'s shape.

Known crash gap: if the API crashes between `runLightSyncPass` returning its result and `db.insert(coachAuditLog)` committing, the retry's `calendar_sync_retried` audit row is **missing** — specifically, the one row that would have carried `{attempted, succeeded, failed}` for that batch. **No lesson row data is lost**: each per-lesson sync wrote its own `calendar_sync_status`, `calendar_sync_error`, `calendar_sync_attempts`, and `last_sync_attempted_at`/`last_sync_succeeded_at` under its own transaction before `runLightSyncPass` returned. **No batch summary**: the aggregate counts are not reconstructable from the lesson rows after the fact without a timestamp bracket (the next retry's row shows cumulative progress, not that batch's slice). The HTTP response to the retry caller is also lost in the crash, so the UI sees a network error and the user triggers a fresh retry on refresh. Connect/disconnect/reconnect audits do **not** have this gap — they commit inside the same transaction as the state change (CLAUDE.md's standard rule), so a crash rolls both back together. Only the retry endpoint carries the deviation.

**Disconnect revokes and keeps the row for reuse, but doesn't touch Google.** Clicking Disconnect calls Google's token revocation endpoint, then in one transaction flips the `coach_calendar_integrations` row's `status` to `'disconnected'`, clears the token fields (`refresh_token_ciphertext`, `refresh_token_iv`, `refresh_token_tag`, `refresh_token_key_version`, `scope`, `google_account_email` → `null`), clears `calendar_sync_status` and `google_calendar_event_id` on future lessons, and writes a `calendar_disconnected` audit row. Only `google_calendar_id` is preserved on the row — so the next connect can reuse the dedicated calendar instead of creating a fresh orphan in the coach's Google account. The account email is refreshed from Google's id_token on reconnect; we don't need to retain the coach's personal address between an explicit disconnect and the next connect. The dedicated Axiom calendar and its events stay in Google untouched — the coach can delete them manually if they want. The status endpoint maps a `'disconnected'` row to `status: 'not_connected'` in its response and hides the calendar id from the client, so the UI shows the Connect button exactly as if no row existed. Reasoning: we don't own data on Google's side once revoked, and silently wiping a coach's calendar on disconnect would be surprising; keeping the row lets reconnect preserve the coach's one calendar across the entire lifecycle. (Note: this applies to explicit coach-initiated disconnect. An out-of-band token revocation leaves the row in `needs_reconnect`, see above.)

## Alternatives considered

- **Full `calendar` scope with explicit calendar id.** Rejected: a bug or compromised token could expose every event the coach can see. `calendar.app.created` is strictly weaker and sufficient.
- **OAuth flow on the web app with API as a token broker.** Rejected: the web app would hold the authorization code briefly, and Supabase SSR cookies plus Google state would need to agree on a round-trip. API-only is simpler and the browser never touches the token.
- **Two-way sync.** Rejected: resolving conflicts between a lesson row and a Google event is a lot of code to serve a case we don't have (the coach doesn't edit lesson times in Google). We may revisit if that changes.
- **Encrypt with libsodium / `secretbox`.** Rejected: AES-256-GCM via Node's built-in `crypto` is standard, FIPS-friendly, and requires no new dependency. We already use `node:crypto` elsewhere (`randomBytes`, `timingSafeEqual`).
- **Store the token with Supabase Vault.** Rejected for v1 — Vault's local-dev story is thin and we'd couple a feature to a Supabase upgrade. Env-key AES is enough; migration to Vault later is a straight re-encrypt.
- **Delete the dedicated Google calendar on disconnect.** Rejected: that calendar may contain context the coach wants, and the scope technically permits it, but silent destructive cleanup is worse UX than leaving a disconnected calendar sitting there.

## Consequences

- Two new tables: `coach_calendar_integrations` (one row per connected coach) and `coach_audit_log` (general coach-level event log — not integration-specific).
- A new `GOOGLE_TOKEN_ENCRYPTION_KEY` env var is a hard dependency — losing it bricks the integration for every connected coach. Document rotation in `docs/plans/google-calendar-sync.md`.
- The deployed API callback is now security-critical. Any change to its path or host requires an update to Google Cloud OAuth settings before deploy.
- Lesson routes gain a hook call, but no transactional dependency on Google — fully reversible if we ever remove the integration.
- Dev `localhost` entry in Google Cloud now points at port 3001 (the API's default `PORT`). No dev-env override is required.
- Coaches whose tokens are revoked out-of-band don't lose their calendar id, scope, or settings — only reconnect is required. Explicit disconnect is still destructive by design.
