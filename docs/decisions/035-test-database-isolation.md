# 035 — Dedicated test Supabase stack

**Date:** 2026-11-06
**Status:** Draft

## Context

Integration tests and manual testing share one local Supabase stack. The 36 integration suites in `apps/api/src/__tests__/integration/` create real auth users through `POST /auth/v1/admin/users`, open real DB connections on `127.0.0.1:54322`, pin the clock with `__setClockForTests`, and POST to `/internal/cron/tick`. Every one of those side effects lands in the same `postgres` database the developer uses for manual testing in `pnpm dev`.

Three symptoms result:

- Rows created by tests pollute the manual UI state. `*@test.local` profiles, dangling audit entries, and orphan households accumulate whenever a test aborts before its cleanup runs.
- Clock-pinned suites (`coachNoShow`, `cronTickLease`, `coachGoogleCalendarSync`, `coachSwimmersLastLesson`, `parentBatchBooking*`) and the cron endpoint promote lessons past their new "now" to `completed` or `no_show`. These changes are indistinguishable from manual actions in Studio and have hit the developer's own lessons more than once.
- There is nothing structural preventing the collision. The existing safety guard in `apps/api/src/__tests__/integration/setup.ts` refuses only *non-local* database URLs; it does not care which local database.

The planning doc at `docs/plans/test-database.md` carries the full migration plan. This ADR records the architectural decisions it depends on.

## Decision

### Run a second Supabase stack dedicated to integration tests

A new `supabase-test/supabase/config.toml` lives at the repo root alongside the existing `supabase/config.toml`. The nested `supabase/` subfolder is what the Supabase CLI's `--workdir` flag expects. The test config sets `project_id = "swim-app-test"` so Docker container names don't collide, and shifts every port by +100 from the defaults (API 54421, DB 54422, shadow 54420, Studio 54423, Mailpit 54424, Mailpit SMTP 54425). Studio, Storage, and Mailpit are disabled in the test stack because no test dials them — every integration test that drains the outbox installs a fake transport via `__setSenderTransportForTests(...)` first (verified across `parentBookingEmails`, `parentBatchBooking*`, `coachAlerts`, and `accountDeletionRealFlows`, whose `drainLessonEmailOutbox()` runs with the fake transport installed earlier in `beforeEach`). The auth service and PostgREST stay on because the test helpers depend on real auth-user creation and sign-in.

Managed by new `pnpm db:test:up` / `db:test:down` / `db:test:status` / `db:test:reset` / `db:test:migrate` / `db:test:sync-catalog` scripts, each of which delegates to the Supabase CLI with `--workdir supabase-test`. The existing `pnpm db:*` scripts continue to manage the manual stack unchanged.

Rough Windows footprint: the slim test stack adds ~700 MB – 1 GB resident memory on top of the manual stack (Postgres ~250 MB plus the auth/api/meta/realtime/analytics/vector/edge containers at ~500 MB; disabled Studio + Storage + Mailpit save ~400 MB). Developers can `pnpm db:test:down` between sessions if Docker Desktop is tight.

Alternatives considered:

- **Separate database inside the same local Postgres.** Rejected as structurally impossible without giving up real-auth coverage. Supabase Auth binds `auth.users` to one database; a `swim_app_test` database alongside `postgres` could not host `profiles.id → auth.users.id`, and the `on_auth_user_created` trigger (ADR 004) that populates profile + household membership runs in the DB where it was installed. Running a second GoTrue to teach it to write to the second DB is Option A with extra steps.
- **Single stack, reset on every run.** Rejected. `supabase db reset` would wipe the developer's manual data on every `pnpm test:integration`. The reset-on-every-run variant of the dedicated-stack option was also rejected as a default because it adds 30–60 s to each invocation during a tight edit-test loop. `pnpm db:test:reset` remains available as a manual escape hatch.
- **Keep the shared stack; harden cleanup.** Rejected. Cleanup bugs are a symptom; the shared stack is the root cause. A test that creates a household and crashes before `cleanup()` runs will leave orphans no matter how thorough the happy-path cleanup is. The existing `createTestUser.cleanup` chain is already carefully ordered around RESTRICT FKs; the issue is not cleanup correctness but containment.

### `apps/api/.env.test` holds the test-stack credentials; `.env` no longer does

`vitest.integration.config.ts` loads `apps/api/.env.test` instead of `apps/api/.env`. `INTEGRATION_DATABASE_URL`, `SUPABASE_URL`, `SUPABASE_PUBLISHABLE_KEY`, and `SUPABASE_SERVICE_ROLE_KEY` move out of `.env` entirely. This keeps the manual-use `.env` strictly a manual-use file — misconfiguring the integration variables in `.env` can no longer accidentally point tests at the manual stack because `.env` is not read by the integration config at all.

`.env.test` is gitignored and generated by the developer from `supabase status --workdir supabase-test -o env`. A committed `.env.test.example` carries placeholders for the four required variables so new contributors see the expected shape without having to grep the test helpers.

### `pnpm test:integration` applies pending migrations and fails fast if the stack is down

The integration script becomes a three-step chain, not a single Vitest invocation:

1. A preflight TCP-connects to the test DB port (from `INTEGRATION_DATABASE_URL`). On `ECONNREFUSED` it prints `Start the test stack with: pnpm db:test:up` and exits non-zero — no Drizzle stack trace, no Vitest prelude, just the command the developer needs.
2. `pnpm db:test:migrate` applies pending migrations against the test stack. Idempotent, so a developer who already migrated loses nothing, and a brand-new migration never surfaces as a cryptic test failure.
3. Vitest runs with the integration config.

A Node wrapper at `apps/api/scripts/runIntegration.ts` owns the chain so Windows developers aren't relying on shell operators.

### Guard integration tests on the test target, not just localhost

`apps/api/src/__tests__/integration/setup.ts` keeps the existing hostname assertion (`localhost`, `127.0.0.1`, or `::1`) and adds a second check: the run is allowed only if `INTEGRATION_DATABASE_URL` contains the test-stack DB port (`:54422/`) or `INTEGRATION_TEST_TARGET=1` is set. The port check catches the local case (anything pointing at 54322 is the manual stack and is refused); the env variable allows CI, whose ephemeral stack still runs on the default port 54322 but is throwaway and therefore safe. A third assertion refuses when `INTEGRATION_DATABASE_URL === DATABASE_URL`, catching a copy-paste where both end up on the same port.

The guard throws in `setup.ts`, which runs once before any test file imports the app, so a wrong target fails before any database connection opens.

Alternatives considered:

- **Guard on database name rather than port.** Rejected. Supabase local stacks always name the database `postgres`; the port is the only differentiator between the two stacks. Introducing a renamed DB would fight the Supabase CLI's conventions and complicate migrations.
- **Guard on an application-level flag written to a DB table.** Rejected as too indirect. The guard has to fail before any DB connection, which rules out anything that requires opening one.

### CI runs one stack, as today

`.github/workflows/integration.yml` continues to run one Supabase stack on the ephemeral runner. The `Run integration tests` step gains `INTEGRATION_TEST_TARGET: "1"` so the new guard allows the default-port stack through. No stack duplication in CI — the runner VM is already the isolation boundary.

## Consequences

- Manual-use data and integration-test data live in physically separate Postgres databases from Phase 1 onward. The two cannot cross over without an explicit `INTEGRATION_DATABASE_URL` edit, and the guard rejects obvious misconfigurations.
- Local Docker footprint grows: a second Supabase stack adds ~1–1.5 GB of resident memory and 5–6 containers to Docker Desktop on Windows. Mitigated by disabling Studio, Storage, and Mailpit in the test stack (none of which the tests dial). Developers who want to save memory between test runs can `pnpm db:test:down`.
- Migrations and catalog sync run twice when the developer wants both stacks current: once via `pnpm db:migrate`, once via `pnpm db:test:migrate`. Scripted so the invocation is symmetric.
- `pnpm db:test:reset` is the standing fix when the test DB accumulates clock-pinned residue. It is not automatic; it runs only when invoked.
- CLAUDE.md gains a one-line rule naming the test stack as the only legal target for `pnpm test:integration`, plus the `pnpm db:test:up` / `pnpm db:test:down` pair and the ~700 MB – 1 GB memory note. Future contributors (human or agent) cannot run integration tests against the manual stack without reading, and then overriding, that rule and the guard behind it.
