# 028 — Parent booking emails via transactional outbox

**Date:** 2026-10-22
**Status:** Accepted

## Context

Six booking state transitions need to produce parent-facing email: request received, lesson confirmed (manual or auto-approved), request declined, request expired, lesson canceled, lesson rescheduled. Today none of these send anything — the stubs in `lib/lessonApproval.ts` (`notifyBookingCreated`, `notifyLessonApproved`, `notifyLessonDeclined`, `notifyCoachOfChange`) are placeholders.

Three constraints shape the design:

- A booking write must never be gated on, roll back from, or wait for an email send. The sender depends on Resend's uptime and on SMTP to Mailpit locally; neither is in the booking's critical path and neither can block a parent from completing a booking during a transport outage.
- An email that logically belongs to a committed booking cannot be lost. "The transaction committed but the email never got queued" would mean a parent books a lesson and never receives confirmation — functionally invisible failure. CLAUDE.md's audit-log rule already codifies this guarantee for `household_audit_log`; emails need the same.
- Nothing in `apps/api` runs service-role-privileged Supabase calls today, and we'd rather not introduce them. The sender needs recipient emails and verification state, but the auth table owns both.

## Decision

**Transactional outbox table — `lesson_email_outbox`.** Every lesson state change writes exactly one outbox row **inside** the same `db.transaction()` as the state change. The row is the durable record that an email needs to be sent; failing to insert it rolls the whole lesson change back. A sender runs after `res.json()` returns and processes the row; the existing cron tick drains anything still `pending`, `failed`, or in an expired-claim `sending` state. The unique key `(lesson_id, event, sequence)` prevents duplicate **rows**; the claim-before-send protocol (next decision below) prevents duplicate **sends**. This is CLAUDE.md's "audit log inside the transaction" rule applied to outbound email. No new worker, no queue, no message bus — same operational surface as every other durable state in the app.

**Claim rows before sending; expired claims are recoverable.** The sender's first operation is to flip the row to `status='sending'` with `claimed_until = now() + interval '2 minutes'` inside a short `FOR UPDATE SKIP LOCKED` transaction, then release the lock, call the transport, then open a short second transaction to flip the row to a terminal state. The drain's row selector picks up `('pending'|'failed')` rows **and** `'sending'` rows whose `claimed_until` has passed, so a crashed sender's row self-heals on the next tick. Reasons the claim is non-optional:

- The dedup key `(lesson_id, event, sequence)` only prevents duplicate *rows*, not duplicate *sends* of a single row. Without the claim, the post-commit microtask and the cron tick can race on the same row and both deliver.
- Holding the DB row lock across the HTTP call starves the Postgres pool under even modest load. The claim decouples lock-hold from send-duration.
- A `claimed_until` timeout is the only durable way to recover from a worker crash mid-send that doesn't involve either infinite stuck rows or a separate reaper process.

The sender also passes the outbox id as Resend's `Idempotency-Key` header, so even if a claim's 2-minute window expires exactly when Resend finished delivering (worst-case race), the retried send is a no-op on Resend's side. The duplicate-send window the earlier draft of this ADR declared "acceptable" is now closed — see "Alternatives considered" for the earlier reasoning.

**Mirror `auth.users.email` + `email_confirmed_at` onto `profiles` instead of adding `SUPABASE_SERVICE_ROLE_KEY` to the API runtime.** The outbox sender needs each recipient's verified email at send time. Two options:

- Mirror: trigger-maintained `profiles.email` + `profiles.email_verified_at` columns, kept in sync by extending the existing `on_auth_user_created` trigger and adding an `on_auth_user_updated` trigger on `UPDATE OF email, email_confirmed_at`. Recipient resolution is a `JOIN profiles ON …` with a nullability filter.
- Service-role: give the API `SUPABASE_SERVICE_ROLE_KEY` and call `supabase.auth.admin.getUserById` for each recipient at send time.

We chose the mirror. The service-role key is a highly-privileged credential whose only use case here is reading two public-ish fields; introducing it to the API runtime expands the privilege surface permanently for a transient need. The mirror is a one-time migration plus two trigger lines, and the sender becomes a plain SQL join. We already extend the signup trigger for related reasons (household creation); adding two columns to its output is cheap.

**React Email templates, HTML + plain-text, no tracking.** Templates live under `apps/api/src/services/emails/templates/<Event>.tsx` and compile via `@react-email/render` to inline-styled HTML plus a plain-text alternative in one call. Reasons: typed props from the outbox payload shape (schema drift between template and payload becomes a type error, not a render-time failure); a built-in preview server that renders every template under Gmail / Outlook / Apple Mail profiles, replacing manual cross-client QA; and the output is vanilla HTML, so swapping Resend for Postmark later is a transport-layer change only. Open- and click-tracking are disabled per Resend API call. No tracking pixel is inserted, no `List-Unsubscribe` header is set (these are transactional, not list traffic), no marketing content lands in the body. The confirmed and rescheduled templates attach an `.ics` body built by a small in-house helper — no new dependency for a format this simple.

**Deterministic `.ics` UID per lesson; monotonic `SEQUENCE` across the lesson's full lifecycle, starting at 0.** UID = `${lesson.id}@axiomaquatics.io`. `lessons.calendar_sequence` stores **the next SEQUENCE value to issue**, defaulting to `0`. Each lesson transaction that writes an outbox row with a non-null `ics_method` snapshots the current value of `calendar_sequence` into the outbox row's `ics_sequence` column, then increments `calendar_sequence` by 1 — all atomically. So the first `REQUEST` ever issued for a lesson ships `SEQUENCE:0`, the first follow-up (reschedule or cancel) ships `SEQUENCE:1`, and so on. This matches RFC 5545's requirement that calendar apps supersede a prior event with the same UID when the new SEQUENCE is strictly greater, so a rescheduled lesson replaces its predecessor in Google Calendar / Apple Calendar / Outlook in place, and a cancel actually removes the invite rather than leaving an orphan. Lessons also carry `calendar_invite_sent_at` so the cancel/decline/expire paths know whether a prior `REQUEST` went out and should emit a `CANCEL`, or whether to send a plain content email with no `.ics` because the lesson was never confirmed.

**No "Add to Google Calendar" deep link.** Confirmed and rescheduled emails ship exactly one calendar path: the `.ics` attachment. Google Calendar, Apple Calendar, Outlook, and Fastmail all parse `.ics` attachments natively, so the deep link added no new capability. It did add surface: a parallel template rendering path that could drift from the `.ics`, and a URL that encodes the lesson's address in a querystring that lives in browser history and Gmail's clipboard. For home-pool lessons the address is a specific family's residence; placing it in a browser-recorded URL is a privacy regression we don't need. Removed.

**Snapshot recipient profile ids at write time, not emails.** The outbox row's `recipient_profile_ids` is a `uuid[]` captured from the household's `owner` + `manager` members inside the lesson transaction. Snapshotting ids (not addresses) means a parent who changes their verified email between the booking write and the sender run receives the email at the current address; a profile that is removed from the household between those two moments still gets the email because they co-owned the lesson at the moment it changed. Email verification is re-checked at send time against the mirrored columns, and profiles with no verified email are quietly skipped (they don't fail the row). This matches "notify who the lesson was for" rather than "notify who is currently a member," which is the ethically clearer behavior for a change event.

**Explicit `APP_ENV` instead of inferring environment from `NODE_ENV`.** `apps/api/src/lib/env.ts` today keys its stricter prod-only validations on `NODE_ENV === "production"`. That rule was correct when the only "production" environment was prod, but Railway's dev service also runs `NODE_ENV=production` (that's how Railway's Node runtime selects the production build flavor of the Node binary and of library bundles — it's not a signal about which deployment this is). We need to tell the dev deploy apart from the prod deploy for env validation and for future per-env behavior.

Introduce `APP_ENV` with values `local` | `dev` | `prod`. All email behavior keys on `APP_ENV`; `NODE_ENV` continues to drive the Node/library build flavor and nothing else. Every current `NODE_ENV === "production"` branch in `env.ts` is renamed to the equivalent `APP_ENV` check (`'prod'`, or `!== 'local'` where the dev deploy should enforce the same validation as prod).

**No recipient allowlist.** The sender does not carry a dev-only recipient filter. On every deployed environment the only gate between an outbox row and a send is `profiles.email_verified_at` being non-null — a parent must have confirmed their Supabase email before any booking email can reach them. On the dev service that means seeded fixtures without a real confirmed inbox never receive mail, which is the behavior we actually want. (An earlier draft of this ADR added a dev-required `EMAIL_ALLOWLIST`; we reversed the decision because it added a parse-time footgun with no additional protection beyond the existing verification requirement.) Local goes to Mailpit regardless.

**Pre-send supersede guard.** Between the claim (step 1 of the sender) and the transport call (step 5), the sender flips a row to the new terminal state `'superseded'` if either is true:

- A newer outbox row for the same lesson has already shipped (`EXISTS (SELECT 1 FROM lesson_email_outbox WHERE lesson_id = :l AND sent_at IS NOT NULL AND created_at > :row.created_at)`). The follow-up email already told the parent the current state; sending the stale one would be noise or an outright contradiction (confirmed arriving after canceled, for instance).
- The lesson's `starts_at` is in the past. In-flight emails for lessons that already began are stale.

**CANCEL rows are exempt from the start-time rule only.** The job of a `METHOD:CANCEL` `.ics` is to clean a stale invite out of the parent's calendar, and a late CANCEL is still correct behavior — leaving the invite stuck would be worse than sending a slightly late apology. CANCEL rows still obey the "newer row already sent" rule (if we already sent anything about the lesson's current state, we don't need to retroactively confirm its removal). This is a one-line conditional, not a separate code path.

**Sequential drain, cap 50, no concurrent sends per tick.** The cron drain awaits each `sendLessonEmailOutboxRow` call before starting the next. Scheduling 50 microtasks at once would launch 50 concurrent Resend calls, risk blowing through Resend's per-second rate limits on a busy tick, and interleave DB writes in a way that makes log correlation hard. Awaiting keeps throughput deterministic (Resend p50 ≈ 150 ms × 50 rows ≈ 7–10 s per tick in steady state), applies backpressure if any single row stalls, and leaves the per-tick budget predictable for the rest of the cron's work.

**No audit log for email events.** `coach_audit_log` and `household_audit_log` are not written for email sends. The outbox row itself is the audit trail: `event`, `attempts`, `last_error`, `sent_at` capture the full lifecycle inline. Writing a parallel audit row would duplicate every field and require either a nested insert or a second transaction, both of which complicate the write path for no new signal. If we later need to show parents a delivery history inside the app, we read the outbox directly — the shape is already compatible with `household_audit_log`'s read patterns.

**No `.ics` on request / decline-from-pending / expire-from-pending.** The spec is `METHOD:REQUEST` for confirmed and rescheduled; `METHOD:CANCEL` for canceled, declined-after-approval, and expired-after-approval. The "after-approval" qualifier is enforced by checking `lessons.calendar_invite_sent_at IS NOT NULL` at write time. Today's state machine (ADR 021) permits decline and expire only from `pending`, so the CANCEL branch is unreachable from a legal transition — but the write logic still handles it defensively, so a future state-machine change that permits `approved → declined` or `approved → expired` doesn't silently leave an invite in the parent's calendar. A pending-only decline or expire sends a plain content email with no attachment.

## Alternatives considered

- **Enqueue the email call directly from the route handler, no outbox table.** Rejected: if the API crashes between `res.json()` and the `queueMicrotask`, the parent never gets the email, and there's no row to show the system that work is pending. The outbox is the only mechanism that survives a crash between commit and send.
- **Service-role Supabase client in the API runtime for recipient lookup.** Rejected on privilege-surface grounds; see "Mirror auth.users.email" above. The additional reason is that a service-role client makes every future endpoint one `supabase.from('auth.users')` away from reading anything in auth, which is a sharp knife we'd rather not keep in the drawer. The mirror narrows the surface to exactly two fields.
- **Store recipient email addresses on the outbox row instead of profile ids.** Rejected: a parent who changes their verified email between the booking write and the sender run would receive the email at the old address, which is confusing and leaks the fact of the earlier address if the row's audit trail is ever surfaced. Profile ids snapshotted at write time + email join at send time preserves both correctness and auditability.
- **Message queue (BullMQ, Postgres LISTEN/NOTIFY-driven worker, SQS).** Rejected: no new infrastructure is a hard requirement, and the cron tick is already running every few minutes with headroom. The outbox-table-as-queue pattern is well-understood and composes with the existing operational model.
- **Separate microservice for email delivery.** Rejected for the same reason, plus the sender has no scaling pressure at the volumes we project (dozens of lessons/day).
- **MJML templates compiled at build time.** Rejected: MJML would add a build step and a runtime dependency on the compiler, and we lose the preview server. React Email's output is comparable (both produce inline-styled HTML tables); the typing and preview tooling tip the balance.
- **Store the `.ics` body on the outbox row at write time.** Considered as a strict "freeze everything render-related" extension of the payload snapshot. Rejected because the `.ics` body includes `DTSTAMP` which is required to be the UTC time at which the event was generated (RFC 5545 §3.8.7.2) — so the body isn't truly frozen anyway, and rendering at send time keeps the row smaller. The outbox freezes the semantic inputs (times, names, UID, SEQUENCE); the `.ics` is a pure function of those plus `now()`.
- **Open- and click-tracking enabled.** Rejected: these are transactional emails to parents of children, and open-tracking inserts a 1x1 image whose request leaks the parent's IP address and user agent to a third party on every open. The marginal signal isn't worth the privacy posture.
- **Accept a known duplicate-send window.** An earlier draft of this ADR left the sender's HTTP call outside any lock and declared the resulting "transport succeeded, result-write failed" window acceptable because `.ics` dedup on UID+SEQUENCE made the duplicate harmless from the parent's calendar perspective. Reversed: a parent receiving two confirmation emails for the same booking (one from the original send, one from the retried send after a crash between the Resend 2xx and the row update) is a quality bug we don't want to ship. The claim-row-first protocol + Resend's `Idempotency-Key` header + the supersede guard close the window at essentially zero code cost.
- **Infer environment from `NODE_ENV`.** Rejected explicitly, as above: Railway's dev service runs `NODE_ENV=production`, so inferring would silently key the production-safe prod validations on the dev deploy. `APP_ENV` is explicit and distinguishes the two deployed environments cleanly.
- **A dev-only `EMAIL_ALLOWLIST` fail-safe.** Rejected on second look. The deliverability gate the sender already enforces — `profiles.email_verified_at` must be non-null — covers the same risk (sending to the full user base on dev) without an env-var footgun. Verified-email records on the dev service only exist for seeded accounts whose confirmation came from a mailbox we control. Adding `EMAIL_ALLOWLIST` on top would double the surface area for a parse-time misconfiguration without raising the safety floor.
- **Keep the "Add to Google Calendar" deep link alongside the `.ics`.** Rejected: the deep link added no new user capability (`.ics` covers every mainstream mail client) and encoded the home-pool address into a querystring that lives in browser history and Gmail's clipboard — a privacy regression relative to the attachment-only path. Removed.
- **Payload lives forever on the outbox row.** Rejected: payloads carry swimmer first names and (for home-pool lessons) full residential addresses. Keeping them indefinitely for sent / skipped / superseded rows gives no new signal 30 days later and expands the surface area of a hypothetical data breach. A cron scrub pass nulls payload on terminal rows older than 30 days while preserving the structured status/attempts/timestamps for audit. A separate rule in `docs/accounts.md` must wire outbox cleanup into the eventual account-deletion flow.

## Consequences

- One new table (`lesson_email_outbox`), two new columns on `lessons` (`calendar_sequence`, `calendar_invite_sent_at`), two new columns on `profiles` (`email`, `email_verified_at`), one updated trigger (`on_auth_user_created`), and one new trigger (`on_auth_user_updated`). Two migrations: one generated, one custom SQL for the triggers.
- Every lesson-mutating route grows an outbox insert inside its existing transaction. The reconcile hook pattern from ADR 027 extends naturally: `queueMicrotask(() => void sendLessonEmailOutboxRow(id))` after `res.json()` — no new middleware, no new route-level glue. The sender's internal claim protocol keeps the microtask and the cron drain from racing.
- The existing `POST /internal/cron/tick` grows two new blocks: a sender drain (sequential, cap 50 per tick) and a payload-retention scrub (cap 500 per tick). The sender drain's row selector picks up expired-claim `'sending'` rows alongside `'pending'`/`'failed'` so a crashed worker self-heals on the next tick.
- `APP_ENV` is introduced as the canonical environment signal. Every `NODE_ENV === "production"` check inside `env.ts` is renamed to the equivalent `APP_ENV` check in the implementation PR. Railway dev and prod services both get `APP_ENV` set explicitly; `NODE_ENV` continues to drive the Node/library build flavor.
- A new runtime dependency: `resend` (dev + prod transport) + `nodemailer` (local SMTP to Mailpit). React Email is a dev dependency plus a tiny `@react-email/render` runtime import.
- Required env vars on prod: `APP_ENV=prod`, `EMAIL_TRANSPORT=resend`, `EMAIL_FROM`, `RESEND_API_KEY`. Required on the dev deploy: the same set with `APP_ENV=dev`. Required locally for the Mailpit path: `APP_ENV=local`, `EMAIL_TRANSPORT=smtp`, `EMAIL_FROM`, `EMAIL_SMTP_HOST`, `EMAIL_SMTP_PORT`.
- The sending domain `send.axiomaquatics.io` is already verified in Resend for Supabase auth email and is reused for both dev and prod booking email. No new DNS or DKIM setup is required.
- Logging rules in `docs/accounts.md` are preserved: no swimmer names, no email addresses, no decline reasons appear in log lines. All sender logs key off `lesson_id` and `outbox_id`.
- Retention: payloads on `'sent'`, `'skipped'`, and `'superseded'` rows older than 30 days are scrubbed by the cron. Account deletion (not yet implemented) must also clear outbox rows for the household being deleted — flag this as a requirement in `docs/accounts.md` when the deletion flow is designed.
- The failure mode "Resend is down" degrades to "emails are delivered a few cron ticks late once Resend recovers." Booking throughput is unaffected. The failure mode "Resend account lost" degrades to "no emails sent, booking works" with the outbox accumulating `'failed'` rows that drain once the account is restored.
- The failure mode "API crashes between the transport 2xx and the result-persist UPDATE" is covered by the claim-expiry + Resend `Idempotency-Key` combination: the retried send is a no-op on Resend's side, so the parent sees exactly one email, and the eventual finalize marks the row `'sent'`.
