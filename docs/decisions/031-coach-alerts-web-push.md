# 031 — Coach alerts via web push

**Date:** 2026-10-27
**Status:** Accepted

## Context

Jason finds out about parent-initiated booking changes by opening the app. The in-app surface works, but he is not sitting at a laptop when a parent cancels a 7 AM lesson at 6:45, and he does not open the dashboard every hour to see whether a new request landed. The existing `notifyCoachOfChange`, `notifyBookingCreated`, `notifyBatchBookingCreated`, and `notifyCoachOfBatchChange` stubs in `apps/api/src/lib/lessonApproval.ts` were left as placeholders by ADRs 028–030 precisely for a feature like this.

Four constraints shape the design:

- A booking write must never be gated on, roll back from, or wait for a push send. Push depends on a third-party service (FCM/APNs via each browser's push service), and no booking transaction can be delayed by Chromium's or Apple's uptime.
- A notification that logically belongs to a committed state change must not be lost. "Jason's phone was asleep and we gave up" would functionally hide a booking from the person responsible for teaching it. CLAUDE.md's audit-log rule applied to the booking email outbox in ADR 028 applies here identically — the alert row is the durable record.
- The same rows that drive push notifications should drive the coach's in-app notification list. One source of truth with read/unread state avoids a parallel "it was pushed but the app says it never happened" bug and lets the coach catch up on a stale phone by opening the app.
- Parent personal information (contact details, email addresses, full home addresses) must not travel through the browser push service in payload. The push service is a third-party processor and the browser decrypts the payload on the lock screen; everything in it is a candidate for a screenshot or an over-the-shoulder read. Swimmer first name + last initial, day, time, and pool name is the minimum useful signal and the ceiling.

## Decision

**One `coach_notifications` table — the durable record for both push delivery and the in-app list.** Every lesson-change path that currently calls a `notify*` stub writes exactly one `coach_notifications` row **inside** the same `db.transaction()` as the state change. The row carries `category`, `urgency`, `payload` (frozen render inputs), a `read_at` timestamp for the in-app list, and the standard outbox-style delivery fields (`push_status`, `push_attempts`, `push_claimed_until`, `push_last_error`, `push_next_attempt_at`, `push_sent_at`). The alert row is the audit trail, the retry anchor, and the row the dashboard renders in the notification list — one shape powers all three. This mirrors the ADR 028 pattern: not a message queue, not a worker, same operational surface as every other durable state in the app.

**Per-subscription delivery, one `coach_push_subscriptions` table.** Each coach device (desktop Chrome, Android Chrome, iOS home-screen installed PWA) registers via the service worker and writes one row keyed by the endpoint URL. Rows carry the endpoint, the browser-generated `p256dh` and `auth` keys, a `profile_id`, a user-agent summary (for the "which devices are enabled" row on `/account`), the subscribed category defaults, and `created_at` / `last_delivery_at` / `last_failure_at`. **Rows are per profile, not coach-only.** The subscription row stores a profile id and the alert sender filters by `profile.role = 'coach'` at send time, so adding parent-facing push later is a matter of writing a new category and a new sender path, not a schema migration. Nothing parent-facing is built in this ADR.

**A notification is `coach_notifications` row N × every active `coach_push_subscriptions` row for that coach.** The alert row is written once per event. The sender fans out across every active subscription for the coach, one `web-push` call per subscription. A send result for a given (notification, subscription) pair is tracked by **updating a per-notification counter plus a per-subscription timestamp** rather than by exploding into a (notification × subscription) join table. The counter model works because the only post-send operations we care about are "mark the notification sent once at least one subscription accepted it" and "remove dead subscriptions when the push service says they are gone." A per-pair audit of which device got which push would be useful eventually, but it is not useful today, and the join row would double the write surface for signal nobody is asking for. (Alternative considered: separate `coach_notification_deliveries` join table. Rejected on the "no abstractions beyond what the task requires" grounds in CLAUDE.md.)

**Standard Web Push with VAPID, the `web-push` library, a service worker, and the existing manifest.** No proprietary APNs/FCM integration — browsers already proxy to the right push service when the service worker calls `PushManager.subscribe()`. The server signs each delivery with a VAPID key pair that is stored in env vars (`VAPID_PUBLIC_KEY`, `VAPID_PRIVATE_KEY`, `VAPID_SUBJECT`). iPhones require the user to add the site to their home screen first — iOS supports Web Push only in installed PWAs on iOS 16.4+ — and the enable flow on `/account` explains this when the browser is iOS Safari and the display mode is not `standalone`. Android Chrome, Chrome on macOS/Windows, Edge, and Firefox all support Web Push directly without the home-screen step. The existing `/icons/site.webmanifest` already declares `"display": "standalone"` and the full icon set required for iOS install, so the manifest is reused with no changes.

**Service worker lives at `/sw.js` on the web app.** Served from `apps/web/public/sw.js` so Next.js emits it at the site root (push subscriptions must be registered under a scope that the SW controls, and the only scope that reliably covers every coach surface is `/`). The SW handles `push`, `notificationclick`, and `pushsubscriptionchange`. The web app registers it from a client component mounted inside the authenticated layout — unauthenticated routes don't need it, and keeping the registration out of the root layout avoids running it on marketing / sign-in flows. The SW's `push` handler reads a minimal payload (title, body, tag, click url, urgency) and calls `self.registration.showNotification`. The SW's `notificationclick` handler calls `clients.openWindow(click_url)` on tap.

**Payload shape sent to the push service is minimal and scrubbed.** The server builds the push body from the alert's `payload` jsonb column but strips it to the fields the lock-screen presentation needs: `title`, `body`, `tag`, `urgency`, `click_url`. The `body` string is composed by the renderer using the lock-screen detail setting (default: swimmer first name + last initial, day, time, pool). The server does **not** send contact information, parent names, decline reasons, or full addresses through the push transport. The data boundary mirrors ADR 027's Google Calendar rule: whatever goes to a third-party processor is the minimum needed for the user to react, and the authoritative information lives behind the deep link in the app. The full `payload` jsonb stays in Postgres and feeds the in-app list.

**Notification tag replaces earlier notifications about the same lesson or batch on the device.** Each push carries a `tag` set to `lesson:<id>` or `batch:<id>`. The browser surface collapses successive notifications with the same tag into a single visible notification, which solves two problems at once: a parent that reschedules a lesson three times in a row produces one visible push, not three, and a user who ignored an earlier push does not need to clear it before the follow-up is visible. The in-app list keeps all three rows (so Jason can audit the history), but the lock screen stays tidy. For "Google Calendar disconnected" and the daily summary push, the tag is `calendar-disconnected:<coachId>` and `daily-summary:<date>` respectively — each has at most one visible instance at a time.

**Only 404 and 410 deactivate a subscription.** `web-push` surfaces 410 Gone and 404 Not Found from the push service when the subscription has been revoked (the user cleared browser data, uninstalled the PWA, or the browser rotated its endpoint). On either response the sender flips the subscription row to `is_active = false` with a `removed_reason` of `'gone'` and does not retry. **Everything else — including VAPID / signature rejections, 400 Bad Request, 403 Forbidden, 413 Payload Too Large, 429 Too Many Requests, and every 5xx — leaves every subscription active and simply fails the send.** VAPID or other signature errors indicate a server-side bug (wrong key, drift between API and web public key, bad `VAPID_SUBJECT`); deactivating subscriptions on those would mass-wipe every registered device the first time the keys get misconfigured, which is exactly the "retrying a config-bug send cannot recover" trap we hit on the email outbox earlier and corrected there. The alert row goes to `push_status='failed'`, the sender logs loudly with the full push-service response code and body excerpt (no payload content, no endpoint URL), and backoff retries pick it up on the next tick. If the problem is a bad VAPID config, the next deploy fixes it and the queued rows drain naturally; if the problem is a bug in the renderer, it fails forever until we fix it — but subscriptions are intact. The account page's "Push notifications" section calls `GET /coach/push/subscriptions` and shows one row per active device plus a "Notifications are off" banner when the coach has zero active subscriptions.

**Alerts are categorized, and the coach can turn each category on or off.** The categories, in alphabetical order so the settings UI reads cleanly: `booking_request` (new parent request, single and per batch), `request_expiring_soon` (pending request approaching `expires_at`), `parent_change` (parent-initiated cancel or reschedule, single and per batch), `calendar_disconnected`, `auto_approved_summary`, `daily_summary`. The `calendar_disconnected` category cannot be turned off — it is operational, not promotional. All others can. Settings live on a `coach_notification_preferences` single-row-per-coach table (one row keyed by profile id) with a boolean per category plus the quiet-hours window and the daily-summary toggle. Defaults match the Decisions-already-made block: everything on, quiet hours 21:00–07:00 Pacific, daily summary on at 08:00 Pacific. **The row is created lazily on first read via an INSERT ... ON CONFLICT DO NOTHING upsert** (`getOrCreateCoachNotificationPreferences(profileId)`), not by a signup trigger — the signup trigger is already crowded with household creation and email mirror writes, and the preferences read happens frequently enough that an upsert on first encounter is simpler to reason about than a backfill-plus-trigger pair. Reads outside the sender's hot path (the settings page, the `/account` form) use the same helper. Changes save optimistically from `/account`.

**Urgency flag is server-computed from the lesson's start time, with a tighter quiet-hours bypass window.** The server marks an alert `urgency = 'urgent'` when the affected lesson's `starts_at` is before midnight tomorrow in `America/Los_Angeles` ("today or tomorrow"). The urgency flag drives three things: it is passed through to the push service as the Web Push `urgency` header (`'high'`), the in-app list renders it with the alert-colored accent per the design system, and the sender passes it through on the push body so the service worker can set `requireInteraction` for lock-screen stickiness. **Only alerts whose affected lesson's `starts_at` is within the next 12 hours bypass quiet hours.** A reschedule that lands tomorrow afternoon is still `urgent` in the UI (today-or-tomorrow) and still ships `urgency: 'high'` to the push service, but it waits for quiet hours to end — Jason does not need a 2 AM buzz for a 4 PM lesson. The two concepts (`urgent` for presentation, `starts_at < now() + 12h` for immediate delivery) are kept distinct so the UI accent and the lock-screen bypass can evolve independently. Batch alerts compute both flags from the earliest affected lesson in the batch.

**Quiet hours hold non-urgent alerts; the daily-summary setting decides whether they ever push individually.** The sender inspects the coach's quiet-hours window at send time: if the alert's `starts_at` is 12 hours or more out (or the alert has no lesson) and the current LA time is inside the quiet window, the sender flips the row to `push_status = 'held'` (new terminal-until-release state) and records `release_at` set to the end of quiet hours. What happens at `release_at` depends on the daily-summary preference:

- **Daily summary ON (the default).** Held alerts are **never pushed individually**. Their in-app list entries remain so the coach can expand "three parent changes while I was asleep" when he opens the app, but the lock-screen push stays silent. The daily summary pass counts held alerts into its payload (`heldAlertCount` in the summary's rendered body: "You have 3 overnight updates. Open the app."). The `releaseHeldCoachNotifications` cron pass still runs — it moves held rows to a new terminal state `'summarized'` once their `release_at` passes, so the drain stops looking at them and the in-app list treats them as read-adjacent (they still appear, they just never pushed).
- **Daily summary OFF.** Held alerts release individually at `release_at` (end of quiet hours). The pass flips them to `push_status='pending'` and the normal drain picks them up. One push per release, no summary.

This resolves the earlier draft's ambiguity about whether `releaseHeldCoachNotifications` double-released alerts that the daily summary already covered. It did; the new state (`'summarized'`) closes the gap, and the branch on `daily_summary_enabled` is where the two paths diverge.

**Daily summary push is composed by the cron, with at-or-past-time semantics and a durable idempotency key.** The cron tick runs `composeDailyCoachSummary` per connected coach on every tick. For each coach the pass computes `now()` in LA, reads the coach's `daily_summary_time_local` (default `08:00`), and fires when **the current LA time is at or past that time AND no `daily_summary` row for the coach exists for today's LA date**. "No row for today" is read from the per-row `(profile_id, dateLocal)` partial unique index — the pass inserts speculatively and the DB rejects duplicates. The tag `daily-summary:<dateLocal>` and the unique index together make the pass idempotent across however many ticks fire inside the 24-hour window; the row is created exactly once per coach per LA date. The payload captures today's approved and completed lessons (first lesson time + pool), count of pending requests awaiting review, count of auto-approved bookings since the last summary, and count of held alerts whose `release_at` passed in the last 24 hours. The renderer produces a one-line push body ("Today: 4 lessons, first at 7:30 at Egret Park. 2 requests waiting."), and the standard drain delivers it. The in-app list entry is the same row — tapping it opens `/coach/schedule`. (Alternative considered: fire only when the UTC minute rounds to the LA target. Rejected because a cron tick that drifts, or a 2-minute gap between ticks, could skip the exact-minute match entirely and the day gets no summary. At-or-past-time with a per-day unique key is strictly more robust.)

**Email backup for booking requests when no push subscription is active.** The default for the `booking_request` category is "on with email backup." At send time, if the coach has zero `is_active = true` push subscriptions, the sender writes an outbox-pattern row to `lesson_email_outbox` instead with a new event, `coach_booking_request`. Jason gets an email with the request details so a half-configured laptop does not leave him blind. The email backup is a per-category boolean on `coach_notification_preferences` (so Jason can turn it off if he wants push-or-nothing); the default is on. The `calendar_disconnected` and `daily_summary` categories do **not** have email backups — the first is already surfaced in the dashboard banner and the second is low priority enough that an email backup would be noise.

**Replace all four stubs with alert inserts.** `notifyBookingCreated(lessonId, autoApproved)` becomes an insert into `coach_notifications` with `category = autoApproved ? 'auto_approved_summary' : 'booking_request'`. `notifyCoachOfChange(lessonId)` branches on the lesson's new status (`canceled`, `rescheduled`) and inserts a `parent_change` row. The two batch stubs insert one row per batch with `batch_id` set and `lesson_id` null (the alert row carries a jsonb payload describing the batch). Every current call site is already inside the state change's transaction, so the replacement is one-line-per-site. The stubs themselves — now thin wrappers around `enqueueCoachNotification` — stay in `apps/api/src/lib/lessonApproval.ts` so the hook contract from ADRs 028–030 is preserved; the implementation is routed through the shared enqueue helper and the stubs no longer "do nothing."

**Expiring-request reminders fire 3 hours before `expires_at`, shifted earlier when the normal time falls in quiet hours.** The cron's `enqueueExpiringRequestReminders` pass picks up pending lessons whose `expires_at` is between 3 and 4 hours from `now()` and enqueues one `request_expiring_soon` row per lesson. If the computed send time (3 hours before expiry) falls inside the coach's quiet-hours window, the reminder is enqueued **before quiet hours start** instead — the alert row is written with `release_at = null`, `push_status = 'pending'`, and `push_next_attempt_at` set to `quiet_hours_start_local - 15 minutes` so Jason gets a chance to act before he goes to bed. A partial unique index on `(profile_id, lesson_id, category) WHERE lesson_id IS NOT NULL` enforces "at most one reminder per lesson" across repeated ticks; the second insert is silently dropped. The shift-earlier rule exists because a request expiring at 10 AM would otherwise fire its "3 hours before" reminder at 7 AM, during the default quiet window, and either silently push past the quiet-hours bypass (confusing) or hold until 07:00 release (too late to be useful). The shift keeps the reminder actionable without punching through quiet hours.

**Deep link per notification.** Tapping a notification opens the relevant page: `booking_request` → `/coach/lessons/<id>` (or `/coach/lessons?batch=<batchId>` for batch requests); `request_expiring_soon` → same as `booking_request`; `parent_change` → the lesson's detail page; `calendar_disconnected` → `/account`; `auto_approved_summary` → `/coach/schedule?view=today`; `daily_summary` → `/coach/schedule`. The deep link is stored on the alert row (`click_url`) at write time so the sender does not need to reconstruct routing.

**No audit log for notification events.** Same reasoning as ADR 028: the alert row's `push_status`, `push_attempts`, `push_last_error`, `push_sent_at`, and `read_at` capture the full lifecycle inline. A parallel `coach_audit_log` row would duplicate every field.

## Alternatives considered

- **Push the state change itself (lesson id, event name) with no server-side composition and compose the body in the service worker.** Rejected. The service worker has no network authentication for a secure API read, and giving the SW an unauthenticated endpoint to compose a lesson summary is a privacy leak surface. Composing the final `title` + `body` server-side keeps the data boundary where every other feature keeps it.
- **Email the coach instead of push.** Rejected as the primary mechanism — Jason is on his phone, mail apps collapse by thread, and 50 bookings/week would turn into 50 inbox entries. Email is kept as the **fallback** when no push subscription is active, per the decision above.
- **SMS via Twilio.** Rejected for now. Carrier reliability is weaker than push, Twilio adds a per-message cost that scales with volume, and the home-screen PWA path solves the iPhone problem without new infrastructure. If Jason's phone ends up with push unreliable in practice, SMS slots into the same outbox pattern as a new transport.
- **A separate `coach_notification_deliveries` join table (one row per push attempt per subscription per notification).** Rejected on YAGNI grounds. We track whether a notification was delivered to at least one device and we track per-subscription health (last success / last failure); we do not currently need to query "which specific device received which specific notification." If that query becomes real, the join table is an additive migration — no restructuring of the current `coach_notifications` row.
- **Store VAPID keys in the database for rotation.** Rejected for v1. Env-var VAPID keys are the standard pattern, rotation is a stop-the-world event (every existing subscription becomes invalid when the public key changes, which forces every coach device to re-subscribe), and the key never leaves the API runtime. A DB-stored key would spread the secret across backups and would still require the stop-the-world rotation. The one-time env var set is simpler.
- **Reuse `lesson_email_outbox` for coach push rows with a `transport` discriminator.** Rejected. The two tables share a lifecycle shape but differ in substance: the email outbox is per lesson or per batch and fans out to recipient profile ids resolved at send time against `profiles.email_verified_at`; the coach alert row is per lesson or per batch and fans out to the coach's device-level subscriptions resolved against `coach_push_subscriptions.is_active`. The join on the second case is to a different table with a different source of truth. Overloading `lesson_email_outbox` to carry push rows would blur the two paths, require the email sender's render logic to branch on transport (and strip to the lock-screen minimum for the push branch), and make the retention scrub rule more complex. The two tables share an operational pattern and a backoff formula, not a schema.
- **Opt-in-per-event (every state change requires the coach to explicitly opt in before the first push can fire).** Rejected. Jason has already asked for alerts; the opt-in friction is the enable flow on `/account` (one tap to grant the browser permission). Per-category defaults are already permissive, and he can turn categories off from the same page.
- **Store the push body (title + body text) on the alert row at write time.** Rejected. The body depends on the coach's lock-screen detail setting at send time, which the coach can change at any point, and composing at send time keeps that live. The payload jsonb is the frozen semantic input; the rendered body is a function of payload + current setting.
- **Lock-screen detail set to "full detail" by default.** Rejected. Lock screens are routinely visible to roommates, kids, and anyone over Jason's shoulder in a public pool deck. The default is "first name + last initial + day + time + pool" — enough to react, not enough to leak. The coach can broaden to full detail (full swimmer name) in settings if the lock screen is only ever his own eyes.

## Consequences

- Three new tables (`coach_notifications`, `coach_push_subscriptions`, `coach_notification_preferences`) and one new value on the `lesson_email_outbox.event` CHECK for the fallback event. **One** generated Drizzle migration — no custom SQL trigger migration. The signup trigger is left alone; coach preference rows are created on first read via `INSERT ... ON CONFLICT DO NOTHING` from the shared `getOrCreateCoachNotificationPreferences(profileId)` helper.
- Every lesson-mutating route grows a `coach_notifications` insert inside its existing transaction — the stubs were already at the correct call sites. The reconcile-hook pattern from ADR 027 extends naturally: `queueMicrotask(() => void sendCoachNotification(id))` after `res.json()`.
- The existing `POST /internal/cron/tick` grows four new blocks: a push-send drain (sequential, cap 50 per tick, same shape as the email drain), a `releaseHeldCoachNotifications` pass that promotes held rows past their `release_at` to either `pending` (daily summary off) or `summarized` (daily summary on), an `enqueueExpiringRequestReminders` pass that scans `pending` lessons whose `expires_at` is 3 to 4 hours out and enqueues a `request_expiring_soon` alert exactly once per lesson (shifted earlier when the computed send time falls in quiet hours), and `composeDailyCoachSummary` which fires per connected coach when the current LA time is at or past the coach's `daily_summary_time_local` and no `daily_summary` row exists for the coach for today's LA date.
- New env vars on every environment: `VAPID_PUBLIC_KEY`, `VAPID_PRIVATE_KEY`, `VAPID_SUBJECT`. Generated via the `web-push generate-vapid-keys` CLI (committed to local `.env`, pasted into Railway variable sets for dev and prod). The public key is also exposed to the web app via `NEXT_PUBLIC_VAPID_PUBLIC_KEY` so the service worker's `subscribe()` call can include it. The private key never leaves the API runtime.
- New runtime dependency on `apps/api`: `web-push`. One peer dependency on `apps/web` for the service worker TypeScript types (`@types/serviceworker`), used only to type the SW source — no runtime addition on the web app since the SW ships as a static file.
- The service worker file `apps/web/public/sw.js` is served at the site root. Any later addition to the SW's responsibilities (background sync, offline cache) requires attention to cache versioning; v1 keeps the SW minimal (push + notificationclick + pushsubscriptionchange only, no fetch handler) so there is no cache story to worry about yet.
- `docs/accounts.md` grows a "Coach data via push" paragraph that spells out the lock-screen content rule and reaffirms the "never log names, emails, or notes" rule for the sender. The parent-facing privacy section is unchanged.
- `docs/data-model.md` gains three table definitions and one column addition. Existing ADRs 027, 028, 029, 030 lesson-change-path lists do not need updating in this doc PR — the push insert sits inside the same transaction as the existing hooks and does not add a new path, only new work at an existing path. The implementation PR will update ADRs 028–030 in the same commit as the code.
- The failure mode "push service rejects everything with 5xx" degrades to "no push, email backup covers booking requests, in-app list still works." Booking throughput is unaffected. The failure mode "VAPID keys misconfigured" degrades to "every send fails with a loudly-logged signature error, every subscription remains active, retries drain naturally once the config is fixed" — subscriptions are only deactivated on 404 or 410 from the push service, never on signature or auth errors. The failure mode "VAPID private key rotated" is a stop-the-world: every existing subscription becomes unusable (the browser's push service rejects the signature), but the subscription rows stay active and the coach re-enables from `/account` on each device; the sender keeps logging and retrying until the coach replaces each subscription with a fresh one that was signed with the new key.
- Payload retention: the alert row's `payload` jsonb is scrubbed by the same cron-driven 30-day retention pass that handles `lesson_email_outbox`. Same rule (`payload = jsonb_build_object('_scrubbed_at', now())` when terminal and >30 days old), same preservation of structured status / timestamps / counters. The in-app list reads scrubbed rows as "This notification is no longer available" after the 30-day mark; v1 renders them as "{category label} · {date}" with no deep-link action because the lesson detail at the other end of the link may itself have moved on.
