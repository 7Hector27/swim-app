# 030 — Parent multi-lesson batch booking (manual + weekly repeat)

**Date:** 2026-10-23
**Status:** Accepted

## Context

Parents who want more than one lesson at a time use the single-lesson flow N times. That means N preview round trips, N confirmation emails, N `.ics` attachments, and N chances for an in-between lesson to steal a slot the parent was about to pick. Jason has asked for a way to put a short stretch of lessons on the schedule in one submission, and the common shape is "every week for a few weeks."

The earlier recurring-lessons plan designed a `lesson_series` rule that generates lessons continuously inside a cron-extended window, with per-occurrence and this-and-future changes, series-level approval, and so on. That shape is heavier than parents actually need right now: no one has asked for an open-ended rule, the this-and-future complexity doubles the write-path, and the cron extension introduces a background generation surface Jason doesn't want to debug yet. A fixed-size batch (up to 10 lessons, never past `bookingMaxAdvanceWeeks`) is a strictly smaller problem that still covers "every Tuesday for a semester" via weekly repeat.

Three constraints frame the design:

- The booking write must stay all-or-nothing. The single-lesson transaction holds an advisory day lock and re-checks the slot engine under the lock before writing. A batch has to extend that discipline across every unique LA day it touches, in deterministic order, without introducing deadlocks against concurrent single-lesson writes.
- The inbox cost of a batch has to be O(1) at the moment of booking. Ten lessons shipping ten confirmation emails and ten `.ics` attachments is noise. One summary email with one `.ics` carrying N `VEVENT`s is the right trade.
- The approval model (ADR 021) and the email + `.ics` sequence model (ADR 028) continue to govern each individual lesson's lifecycle after the batch is written. Nothing about batch booking should rewrite how a single lesson is rescheduled, canceled, or synced to Google Calendar.

## Decision

**Parents only. Jason uses `/coach/book` for his own bookings per ADR 029.** The batch path is `POST /lessons/batch`, mounted on the parent-facing router with `requireUser → requireParent → requireHouseholdMember → validate`. Coach bookings are a different ergonomic (no notice window, per-pick warnings, server-computed override object) and belong on the coach surface. Single-lesson parent booking at `POST /lessons` stays exactly as it is — no caller changes, no routing branch.

**Per batch: one household, one swimmer set, one pool, one duration.** Everything else is shared across the picks. If a parent wants two swimmers at the same pool for a weekly cadence, they submit one batch. If they want a different swimmer set or a different pool, they submit a second batch. This keeps the preview and submit payloads small, the `.ics` summary coherent, and the trust check (which is pool-scoped per ADR 021) a single yes/no per batch.

**Two batch modes: `manual` and `weekly`.** Manual carries an explicit array of 2–10 `(startsAt)` picks. Weekly carries a single `firstStartsAt` plus an integer `weeks` (2–10), capped by the server at `min(weeks, bookingMaxAdvanceWeeks ÷ 7, 10)` — the cap is applied silently when the parent's request would overshoot. Mode is stored on `booking_batches.mode` so the email copy can distinguish "weekly lessons starting <date>" from "N lessons at <pool>," and so later changes have a signal for whether the batch was meant to be recurring.

**Preview before submit lists every pick with a state and, when relevant, suggestions.** `POST /lessons/batch/preview` runs the slot engine for each candidate pick and returns an array of `{ index, startsAt, state, reason?, suggestions? }`. States mirror the existing slot engine (`available`, `too_soon`, `past`, `not_open_yet`, `outside_hours`, `blocked_time`, `day_closed`, `unavailable`) plus one new value `conflicts_batch` for a pick that overlaps another pick in the same submission under duration + travel buffer + daily cap. Suggestions, when the pick is not available, are up to three nearby open slots on the same LA day — the UI lets the parent click one to replace the flagged pick, or skip the week (weekly mode) / remove the pick (manual mode). Preview is a pure read with no lock and no row writes, so parents can iterate.

**Submit uses per-day advisory locks for every unique LA date, taken in ascending calendar order.** This is the single-lesson rule applied N times. Ascending order is the key invariant: two concurrent submissions (another parent, or the single-lesson path) that touch overlapping dates always acquire locks in the same order, so there is no deadlock. Under the locks, the server re-runs `computeAvailableSlots` for each pick with the batch's other picks folded in as if they were already approved lessons — the batch's picks must be mutually consistent on travel buffer, same-coach overlap, and daily lesson-minute cap even though none of them is on the DB yet. If any pick fails the recheck, the whole transaction rolls back and the response is a 422 `picks_conflict` with a per-pick list the UI can reconcile.

**All-or-nothing. No partial batches.** The transaction either writes `booking_batches` + N `lessons` + N `lesson_swimmers` + one `household_audit_log` + one `lesson_email_outbox` row and commits, or it writes nothing. Partial writes would leave the summary email referring to lessons that don't exist, split the audit record, and create a UX where the parent sees "4 of 7 lessons booked" and has to re-pick the other 3 blind. The parent re-runs preview after seeing conflicts, picks replacements, and re-submits.

**Approval under ADR 021 is pool-scoped and runs once per batch.** `needsApproval(householdId, locationId)` is called before writing any lesson. If `false`, every lesson lands as `status='approved'` with `approved_at=now()`, `approved_by=NULL` (system auto-approval, same semantics as single-lesson auto-approval). If `true`, every lesson lands as `pending` with the standard `expires_at = starts_at − 16h`. Pending expiry is per-lesson from that point on — the existing cron expiry pass handles them individually without any batch awareness. Mixed states can arise over time (a parent reschedules one approved batch lesson into a pending state, or a coach approves some via `PATCH /coach/lessons/:id/approve` before the others), and the model handles that cleanly: `batch_id` is just a nullable link, not a lifecycle constraint.

**Coach "approve all pending in a batch" as a convenience path.** `PATCH /coach/lessons/batch/:batchId/approve-pending` runs one transaction that selects pending batch lessons `FOR UPDATE`, flips them to `approved` with `approved_by = <coach>`, snapshots each one's `calendar_sequence` and increments it, writes one `household_audit_log` row with `action='lesson_batch_approved'` and a payload listing the newly-approved lesson ids, and inserts one `lesson_email_outbox` row with `event='batch_approved'`. The sender renders a single summary email with one `.ics` carrying `METHOD:REQUEST` and one `VEVENT` per newly-approved lesson (each with its own per-lesson UID and the just-incremented sequence). The coach retains the per-lesson approve route for the case where they want to approve 2 of 3 — approve-all is additive, not a replacement.

**One `booking_batches` table, one new `lessons.batch_id` nullable FK, no new `lesson_` columns.** The schema change is: a new `booking_batches` row carrying `(id, household_id, created_by, mode, created_at, updated_at)`, and a nullable `lessons.batch_id uuid REFERENCES booking_batches(id)` with `ON DELETE RESTRICT`. The batch row is immutable after insert — if the parent cancels remaining lessons, the batch itself persists for audit, and the member lessons' `status` changes individually. Nothing else on `lessons` changes.

**`lesson_email_outbox` extends to carry batch-scoped rows.** The decision is:

- `lesson_id` becomes nullable.
- A new column `batch_id uuid REFERENCES booking_batches(id)` is added, nullable.
- A `CHECK ((lesson_id IS NOT NULL)::int + (batch_id IS NOT NULL)::int = 1)` enforces exactly one of them is set. Every row is either a per-lesson event or a per-batch event; never both.
- The existing `UNIQUE (lesson_id, event, sequence)` constraint is replaced by two partial unique indexes: one on `(lesson_id, event, sequence) WHERE lesson_id IS NOT NULL`, one on `(batch_id, event, sequence) WHERE batch_id IS NOT NULL`. Per-lesson dedup and per-batch dedup are independent namespaces, which matches how a parent reads them: "did we already send the batch summary?" is one question, "did we already send the reschedule?" is another.
- The CHECK on `event` grows two values: `'batch_booked'` and `'batch_approved'`.
- Batch rows carry `ics_method = NULL` and `ics_sequence = NULL` on the row itself (the paired-nullability CHECK continues to hold). The renderer, when it sees an event in the batch set, reads the per-lesson `calendar_sequence` values from `payload.lessons[]` (snapshotted at write time) and builds a `VCALENDAR` with one `VEVENT` per confirmed lesson. The per-lesson UID (`${lessonId}@axiomaquatics.io`) and sequence are preserved so later per-lesson reschedules and cancels can supersede specific `VEVENT`s via the existing `SEQUENCE:N` rule.

**Supersede guard, updated for batch rows.** The current guard (ADR 028) is "flip to `superseded` if a newer outbox row for this `lesson_id` has already sent, or the lesson's `starts_at` is in the past." For a batch row:

- Supersede if a newer batch outbox row for the same `batch_id` has already sent (`EXISTS newer sent row with same batch_id`). Keeps the inbox tidy when `batch_booked` + `batch_approved` could in principle both be in flight.
- Supersede if every lesson in the batch is either in a terminal non-active state (`canceled`, `declined`, `expired`, `no_show`) or has `starts_at < now()`. In other words: if there is nothing left in the future to put on the parent's calendar, the summary is stale.

The second rule intentionally does not care about any single lesson's state. A batch that was all-approved at submit time can lose a lesson to a reschedule-rollback-to-pending (ADR 028 row 4) and still ship the summary — the summary describes the moment the batch was booked, not the live state of each lesson.

**No per-lesson `booking_requested` or `lesson_confirmed` rows for batch lessons.** The outbox-write path at `POST /lessons/batch` writes exactly one row (`batch_booked`) regardless of the mix of approved and pending lessons. The sender resolves recipients, renders the summary, builds the multi-`VEVENT` `.ics`, and sends. Zero per-lesson emails fire at batch creation time. Later per-lesson state changes (reschedule, cancel, individual approval, expiry) continue to emit their own per-lesson events exactly as they do today — ADR 028's rules apply unchanged from that point. The parent's inbox: one email at creation, then standard per-lesson emails for later changes.

**Approve-all emits exactly one `batch_approved` row.** Same shape: one row, one summary email, one `.ics` with `VEVENT`s for the newly-approved lessons only. Lessons that were already approved before approve-all ran are not re-invited (nothing in their state has changed). If the batch had zero pending lessons at the moment approve-all ran, the handler returns 409 `no_pending_lessons`.

**Optional parent "cancel remaining lessons in this batch."** `DELETE /lessons/batch/:batchId/remaining` cancels future-dated `approved` and `pending` batch lessons in one transaction, writes N per-lesson `lesson_canceled` outbox rows (per the decision above that later changes send per-lesson emails), and writes one `household_audit_log` row. **Marked optional for v1.** If Jason wants it before v1 ships, it's a short add; if he'd rather test the batch creation path first and defer the cancel, we ship v1 without it and the parent cancels lessons individually. Open question flagged.

**Google Calendar sync fires per approved lesson after commit.** No batch-level sync surface — `syncLessonToGoogle(id)` is already idempotent per-lesson, and queuing N microtasks after `res.json()` is identical to how ADR 029's coach-booking path handles its single lesson, repeated N times. The 100 ms sequential gap inside the sync service keeps burst traffic under Google's quota comfortably even for a 10-lesson batch. Add `/lessons/batch`, `/coach/lessons/batch/:batchId/approve-pending`, and (if it ships) `/lessons/batch/:batchId/remaining` to ADR 027 and ADR 028's lesson-change-path lists in the same commit as the implementation.

## Alternatives considered

- **Keep the `lesson_series` design from the recurring-lessons plan and ship weekly repeat as a specialization.** Rejected because the heavy pieces of that plan (cron extension window, per-occurrence vs this-and-future, open-ended series, generation state on the series row, `generated_through_date`, `lesson_series_skips`) are not needed to serve "every Tuesday for the next 8 weeks." A batch with a fixed `weeks` cap is strictly smaller and avoids a background generation surface. The recurring-lessons plan is shelved; if an open-ended rule becomes a real need later, we build it on top of batch rather than instead of it.
- **Per-lesson `booking_requested` and `lesson_confirmed` emails even inside a batch.** Rejected on inbox-noise grounds and on the pragmatic observation that parents want one artifact per booking action, not N. The information in a single summary with a multi-`VEVENT` `.ics` is strictly a superset of what the N per-lesson emails would carry, minus the duplication. Flagged in open questions in case Jason specifically wants per-lesson emails for his own visibility (he already gets per-lesson Google Calendar events; this would duplicate that signal into his email).
- **Allow multi-pool batches with per-lesson approval.** Rejected for v1. Multi-pool batches would mean `needsApproval` runs once per unique pool in the batch, the summary email has to group by pool, and the approve-all affordance has to be scoped per pool. The complexity cost is real and the use case ("a parent books Egret Park on Tuesdays and Swallows Park on Thursdays in the same submission") is speculative. The batch stays one-pool for v1; if Jason wants mixed later, the schema already supports it — `batch_id` doesn't carry pool, each lesson row does — and the add is scoped to the submit and preview endpoints.
- **A new `batch_canceled` outbox event and summary email for cancel-remaining.** Rejected consistently with the "later changes send per-lesson emails" rule. Flagged in open questions because for a 10-lesson cancellation the per-lesson approach is noisy, and if Jason confirms that a single summary is nicer, the add is one event + one template.
- **Row-locking the batch's lessons with `FOR UPDATE` instead of advisory day locks.** Rejected because the slot engine has to re-check availability against all pending/approved lessons in a day, which means we need to serialize per-day writes system-wide — not per-row. `pg_advisory_xact_lock(hashtext('lesson-day:' + laDate))` is the mechanism single-lesson booking already uses; extending it to batch is a trivial loop. Row locks on the batch's own lessons would protect nothing (the rows don't exist yet) and introduce a different lock domain than single-lesson booking.
- **Writing per-lesson outbox rows that reference `batch_id` AND the lesson id.** Rejected because the dedup key `(lesson_id, event, sequence)` + the pre-send supersede guard already handle per-lesson events for every state change downstream of the batch. Carrying `batch_id` on a per-lesson row would be a second grouping handle that no reader needs, with no clear invariant for when to populate it (every reschedule of a batch lesson? only the first? never after cancel?). The CHECK that exactly one of `lesson_id` / `batch_id` is non-null keeps the two namespaces cleanly separated.
- **Store `.ics` method and sequence on the batch outbox row and ignore `payload.lessons`.** Rejected because a batch row's `.ics` has multiple `VEVENT`s, each with its own UID and sequence pulled from the specific lesson. A single `(ics_method, ics_sequence)` pair on the row can't represent that; stuffing it with one of the lessons' values would be arbitrary and would break the paired-nullability invariant. Reading sequences from `payload.lessons` at render time is the simplest working model.
- **A single `booking_batch_members` junction table instead of `lessons.batch_id`.** Rejected because every batch member is already a lesson row, and every lesson belongs to at most one batch. A junction with cardinality `(1, 0..1)` is a column, not a table.

## Consequences

- One new table (`booking_batches`), one new column (`lessons.batch_id`), two added columns on `lesson_email_outbox` (`batch_id` plus `lesson_id` becoming nullable), one replaced constraint (the outbox's UNIQUE becomes two partial unique indexes), two new values in the outbox `event` CHECK (`batch_booked`, `batch_approved`), two new values in the `household_audit_log.action` free-text column (`lesson_batch_booked`, `lesson_batch_approved`, plus `lesson_batch_canceled_remaining` if the optional endpoint ships). One generated Drizzle migration and no backfill — existing per-lesson outbox rows all carry `lesson_id`, so the new CHECK is satisfied automatically.
- Three new parent-facing API endpoints: `POST /lessons/batch/preview`, `POST /lessons/batch`, and (optionally for v1) `DELETE /lessons/batch/:batchId/remaining`. One new coach-facing endpoint: `PATCH /coach/lessons/batch/:batchId/approve-pending`. All Zod-validated via `packages/shared/src/schemas/booking.ts`.
- ADR 027's lesson-change-path list grows by the batch write path (per-lesson sync hooks for each approved batch member) and by the approve-all path. ADR 028's list grows the same way, plus the new `batch_booked` and `batch_approved` events the sender's render path must handle. The follow-up PR that implements this plan updates both ADRs in one doc commit.
- The parent-facing booking surface in the web app grows a batch flow with a mode toggle (manual / weekly), a per-pick preview with inline conflict resolution, and a lessons-grouped-by-batch view on the dashboard. The single-lesson flow is unchanged and remains the default; the batch path is a new entry.
- The sender's render path gains a batch branch — one new template (shared by `batch_booked` and `batch_approved` with a header/subject variant), one new `.ics` build helper that composes `VEVENT`s from `payload.lessons[]`. React Email's preview server exercises the new template cross-client in the same way as the single-lesson templates.
- The outbox retention scrub (ADR 028, 30-day payload nullification on terminal rows) applies to batch rows without changes: the payload on a terminal batch row is nulled at the 30-day mark alongside its per-lesson siblings.
- The recurring-lessons plan at `docs/plans/recurring-lessons.md` is marked **shelved** by this ADR. It stays in the repo as reference material for the open-ended series shape — if Jason wants a true recurring rule later, that doc is where the design starts.
