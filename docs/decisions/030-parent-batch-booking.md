# 030 — Parent multi-lesson batch booking (manual + weekly repeat)

**Date:** 2026-10-23
**Status:** Accepted (revised 2026-10-23)

## Context

Parents who want more than one lesson at a time use the single-lesson flow N times. That means N preview round trips, N confirmation emails, N `.ics` attachments, and N chances for an in-between lesson to steal a slot the parent was about to pick. Jason has asked for a way to put a short stretch of lessons on the schedule in one submission, and the common shape is "every week for a few weeks."

The earlier recurring-lessons plan designed a `lesson_series` rule that generates lessons continuously inside a cron-extended window, with per-occurrence and this-and-future changes, series-level approval, and so on. That shape is heavier than parents actually need right now: no one has asked for an open-ended rule, the this-and-future complexity doubles the write-path, and the cron extension introduces a background generation surface Jason doesn't want to debug yet. A fixed-size batch (2–20 lessons, every lesson strictly inside `bookingMaxAdvanceWeeks`) is a strictly smaller problem that still covers "every Tuesday for a semester" via weekly repeat.

Three constraints frame the design:

- The booking write must stay all-or-nothing. The single-lesson transaction holds an advisory day lock and re-checks the slot engine under the lock before writing. A batch has to extend that discipline across every unique LA day it touches, in deterministic order, without introducing deadlocks against concurrent single-lesson writes.
- The inbox cost of a batch has to be O(1) at the moment of booking. Twenty lessons shipping twenty confirmation emails and twenty `.ics` attachments is noise. One summary email with one `.ics` carrying N `VEVENT`s is the right trade.
- The approval model (ADR 021) and the email + `.ics` sequence model (ADR 028) continue to govern each individual lesson's lifecycle after the batch is written. Nothing about batch booking should rewrite how a single lesson is rescheduled, canceled, or synced to Google Calendar.

## Decision

**Parents only. Jason uses `/coach/book` for his own bookings per ADR 029.** The batch path is `POST /lessons/batch`, mounted on the parent-facing router. Coach bookings are a different ergonomic (no notice window, per-pick warnings, server-computed override object) and belong on the coach surface. Single-lesson parent booking at `POST /lessons` stays exactly as it is — no caller changes, no routing branch.

**Owner and manager only on the server. Viewers get 403.** The batch write endpoints resolve `req.householdRole` via the existing `requireHouseholdMember` middleware and then explicitly reject `viewer`. This matches the single-lesson booking rules and the household-role table on `docs/plans/phase-2-booking.md`'s permission summary. Viewers never create, approve-all, or cancel-remaining a batch; they can still see batch lessons in read-only views because those read paths predate this ADR.

**Per batch: one household, one swimmer set, one pool, one duration.** Everything else is shared across the picks. If a parent wants two swimmers at the same pool for a weekly cadence, they submit one batch. If they want a different swimmer set or a different pool, they submit a second batch. This keeps the preview and submit payloads small, the `.ics` summary coherent, and the trust check (which is pool-scoped per ADR 021) a single yes/no per batch.

**The cap is 2–20 lessons, counted in lessons rather than weeks.** Manual picks: `picks.length ∈ [2, 20]`. Weekly: `weekdays.length * weeks` must land in `[2, 20]` at the schema level. The 20-lesson ceiling is a reasonable upper bound for a trimester-sized batch; it also keeps the sync-service burst (one `syncLessonToGoogle` microtask per approved lesson with the sync service's existing 100ms gap) safely under Google's user quota.

**Two batch modes: `manual` and `weekly`.** Manual carries an explicit array of start times. Weekly carries a `timeOfDay` (local time string), a `weekdays` array of ISO weekday numbers (1=Mon … 7=Sun; one or more), a `startDate` (LA calendar date), and a `weeks` count — the server expands these into `weekdays.length * weeks` candidate lessons at that `timeOfDay` on each listed weekday in each listed week. **Multiple weekdays at one time of day is supported** (for example, Tue + Thu at 4:30 PM for 8 weeks → 16 lessons). Mode is stored on `booking_batches.mode`, and for weekly batches the chosen `weekdays`, `timeOfDay`, `startDate`, and `weeks` are stored on `booking_batches` so later features (coach grouping, cancel-remaining summary) know what the parent originally asked for.

**Weekly never caps silently. Every lesson must fall inside `now + bookingMaxAdvanceWeeks`.** The preview endpoint classifies any candidate lesson whose `startsAt` is past the booking window as `not_open_yet` and returns it in the picks array alongside the others, with a clear flag the UI surfaces (for example, "3 of your 16 lessons fall outside Jason's 10-week booking window and will not be booked. Book them closer to the date or shorten the series.") The submit endpoint **rejects** any batch where any picked lesson is past the window — there is no server-side truncation. The earlier draft of this ADR mentioned a `÷ 7` formula and silent capping; both are gone. The parent chooses what to do with the over-window lessons: shorten the batch, start later, or skip the specific weeks that fall past the window.

**Preview before submit lists every pick with a state and, when relevant, suggestions.** `POST /lessons/batch/preview` runs the slot engine for each candidate pick and returns an array of `{ index, startsAt, state, reason?, suggestions? }`. States mirror the existing slot engine (`available`, `too_soon`, `past`, `not_open_yet`, `outside_hours`, `blocked_time`, `day_closed`, `unavailable`) plus `conflicts_batch` for a pick that overlaps another pick in the same submission under duration + travel buffer + daily cap. Every weekly-mode lesson appears individually in the preview so the parent can move or skip each one independently — "move this Tuesday to Wednesday" is just as supported as "move this Tuesday to 5 PM instead of 4:30 PM." Suggestions, when the pick is not available, are up to three nearby open slots on the same LA day. Preview is a pure read with no lock and no row writes.

**Submit uses per-day advisory locks for every unique LA date, taken in ascending calendar order.** This is the single-lesson rule applied N times. Ascending order is the key invariant: two concurrent submissions (another parent, or the single-lesson path) that touch overlapping dates always acquire locks in the same order, so there is no deadlock. Under the locks, the server re-runs `computeAvailableSlots` for each pick with the batch's other picks folded in as if they were already approved lessons — the batch's picks must be mutually consistent on travel buffer, same-coach overlap, and daily lesson-minute cap even though none of them is on the DB yet. If any pick fails the recheck, the whole transaction rolls back and the response is a 422 `picks_conflict` with a per-pick list the UI can reconcile.

**All-or-nothing. No partial batches.** The transaction either writes `booking_batches` + N `lessons` + N `lesson_swimmers` + one `household_audit_log` + one `lesson_email_outbox` row and commits, or it writes nothing. Partial writes would leave the summary email referring to lessons that don't exist, split the audit record, and create a UX where the parent sees "4 of 7 lessons booked" and has to re-pick the other 3 blind. The parent re-runs preview after seeing conflicts, picks replacements, and re-submits.

**Approval under ADR 021 is pool-scoped and runs once per batch.** `needsApproval(householdId, locationId)` is called before writing any lesson. If `false`, every lesson lands as `status='approved'` with `approved_at=now()`, `approved_by=NULL` (system auto-approval, same semantics as single-lesson auto-approval). If `true`, every lesson lands as `pending` with the standard `expires_at = starts_at − 16h`. Pending expiry is per-lesson from that point on — the existing cron expiry pass handles them individually without any batch awareness. Mixed states can arise over time (a parent reschedules one approved batch lesson into a pending state, or a coach approves some via `PATCH /coach/lessons/:id/approve` before the others), and the model handles that cleanly: `batch_id` is just a nullable link, not a lifecycle constraint.

**Coach "approve all pending in a batch," surfaced as a grouping on the pending list.** `PATCH /coach/lessons/batch/:batchId/approve-pending` runs one transaction that selects pending batch lessons `FOR UPDATE`, flips them to `approved` with `approved_by = <coach>`, snapshots each one's `calendar_sequence` and increments it, writes one `household_audit_log` row with `action='lesson_batch_approved'`, and inserts one `lesson_email_outbox` row with `event='batch_approved'`. The coach's pending-lessons UI groups rows by `batch_id`; each batch group gets an "Approve all" action alongside the per-lesson approve/decline. The grouping and the convenience endpoint ship in Phase 3; approve-all is additive, not a replacement for the per-lesson route.

**Parent cancel-remaining ships in v1 with its own summary email.** `DELETE /lessons/batch/:batchId/remaining` cancels future-dated `approved` and `pending` batch lessons in one transaction and emits **one** `batch_canceled` outbox row with a `METHOD:CANCEL` `.ics` carrying one `VEVENT` per canceled lesson (each `VEVENT` uses its own per-lesson UID and the lesson's incremented `calendar_sequence`). This replaces the per-lesson cancel emails that the earlier draft of this ADR proposed for this path — the inbox-count argument that justified the one-summary email for `batch_booked` applies equally to the inverse operation. Per-lesson cancel emails for individual (non-cancel-remaining) cancels through `DELETE /lessons/:id` remain unchanged.

**One `booking_batches` table, one new `lessons.batch_id` nullable FK, no new `lesson_` columns.** The batch row carries:

| Column | Purpose |
|---|---|
| `id` | PK |
| `household_id` | FK → households (RESTRICT) |
| `created_by` | FK → profiles (the parent who submitted) |
| `mode` | `'manual' | 'weekly'` |
| `weekly_weekdays` | `int[]` nullable: ISO weekday numbers for weekly mode, NULL for manual |
| `weekly_time_of_day` | `time` nullable: local time (America/Los_Angeles) for weekly mode, NULL for manual |
| `weekly_start_date` | `date` nullable: LA calendar date for weekly mode, NULL for manual |
| `weekly_weeks` | `int` nullable: number of weeks for weekly mode, NULL for manual |
| `created_at`, `updated_at` | standard |

A CHECK ensures the weekly columns are all non-null for `mode='weekly'` and all null for `mode='manual'`. The batch row is immutable after insert; member lessons' lifecycle is separate.

**`lesson_email_outbox` extends to carry batch-scoped rows.**

- `lesson_id` becomes nullable.
- A new column `batch_id uuid REFERENCES booking_batches(id) ON DELETE RESTRICT` is added, nullable.
- A `CHECK ((lesson_id IS NOT NULL)::int + (batch_id IS NOT NULL)::int = 1)` enforces exactly one of them is set.
- The existing `UNIQUE (lesson_id, event, sequence)` constraint is replaced by two partial unique indexes: one on `(lesson_id, event, sequence) WHERE lesson_id IS NOT NULL`, one on `(batch_id, event, sequence) WHERE batch_id IS NOT NULL`. Per-lesson dedup and per-batch dedup are independent namespaces.
- The CHECK on `event` grows **three** values: `'batch_booked'`, `'batch_approved'`, `'batch_canceled'`.
- Batch rows carry `ics_method = NULL` and `ics_sequence = NULL` on the row itself (the paired-nullability CHECK continues to hold). The renderer, when it sees an event in the batch set, reads the per-lesson `calendar_sequence` values from `payload.lessons[]` (snapshotted at write time) and builds a `VCALENDAR` with one `VEVENT` per included lesson. The per-lesson UID (`${lessonId}@axiomaquatics.io`) is preserved so later per-lesson reschedules can supersede specific `VEVENT`s via the existing `SEQUENCE:N` rule.

**Send-time VEVENT filter.** When the sender renders a `batch_booked`, `batch_approved`, or `batch_canceled` row's `.ics`, it filters `payload.lessons[]` down to the lessons that **still** match the snapshot: for `batch_booked` and `batch_approved`, keep lessons whose current `status='approved'`, whose `starts_at > now()`, and whose `calendar_sequence` equals the sequence snapshotted at write time; for `batch_canceled`, keep lessons whose current `status='canceled'` and whose `calendar_sequence` equals the snapshot (CANCEL rows are correct even post-start-time, matching ADR 028). Lessons that have been rescheduled, canceled, re-approved, or otherwise changed between the batch write and the sender's run are dropped from this `.ics` — they have already had (or will have) their own per-lesson `.ics` through the normal per-lesson outbox events. Reason: the summary `.ics` is a snapshot of the batch at a moment in time; stale `VEVENT`s in it would either duplicate an event the parent already received a correct per-lesson invite for, or re-invite an event that no longer exists. The filter runs in-memory from the live `lessons` table at send time; it does not require re-reading the batch.

**Supersede guard, updated for batch rows.** The current guard (ADR 028) is "flip to `superseded` if a newer outbox row for this `lesson_id` has already sent, or the lesson's `starts_at` is in the past." For a batch row:

- Supersede if a newer batch outbox row for the same `batch_id` has already sent (`EXISTS newer sent row with same batch_id`). Keeps the inbox tidy when `batch_booked` + `batch_canceled` could in principle both be in flight.
- Supersede if every lesson in the batch is either in a terminal non-active state (`canceled`, `declined`, `expired`, `no_show`) or has `starts_at < now()` **and** the row is not `batch_canceled`. CANCEL rows exempt from the start-time rule, matching ADR 028's exemption for `METHOD:CANCEL`.
- Supersede if the send-time filter reduces `payload.lessons[]` to zero eligible lessons. There is nothing to attach, nothing to confirm, nothing to cancel.

**No per-lesson `booking_requested` or `lesson_confirmed` rows for batch lessons.** The outbox-write path at `POST /lessons/batch` writes exactly one row (`batch_booked`) regardless of the mix of approved and pending lessons. Zero per-lesson emails fire at batch creation time. Later per-lesson state changes (reschedule, individual approval, cancel through `DELETE /lessons/:id`, expiry) continue to emit their own per-lesson events exactly as they do today — ADR 028's rules apply unchanged from that point. The parent's inbox: one email at creation (`batch_booked`), optionally one when the coach runs approve-all (`batch_approved`), one if the parent uses cancel-remaining (`batch_canceled`), and the normal per-lesson emails for anything else.

**Google Calendar sync fires per approved lesson after commit.** No batch-level sync surface — `syncLessonToGoogle(id)` is already idempotent per-lesson, and queuing N microtasks after `res.json()` is identical to how ADR 029's coach-booking path handles its single lesson, repeated N times. Add `/lessons/batch`, `/coach/lessons/batch/:batchId/approve-pending`, and `/lessons/batch/:batchId/remaining` to ADR 027 and ADR 028's lesson-change-path lists in the same commit as the implementation.

## Alternatives considered

- **Keep the `lesson_series` design from the recurring-lessons plan and ship weekly repeat as a specialization.** Rejected because the heavy pieces of that plan (cron extension window, per-occurrence vs this-and-future, open-ended series, generation state on the series row, `generated_through_date`, `lesson_series_skips`) are not needed to serve "every Tuesday for the next 8 weeks." A batch with a fixed `weeks` cap is strictly smaller and avoids a background generation surface. The recurring-lessons plan is shelved; if an open-ended rule becomes a real need later, we build it on top of batch rather than instead of it.
- **Silently cap weekly `weeks` to fit `bookingMaxAdvanceWeeks`.** Rejected on the second pass of this ADR. Silent capping hides from the parent the fact that they asked for lessons the system cannot create — "I asked for 12 weeks and got 7" is a feature regression dressed up as politeness. The preview flagging over-window lessons as `not_open_yet` with an inline count lets the parent see what the system can and cannot do and decide how to react.
- **Per-lesson `booking_requested` and `lesson_confirmed` emails even inside a batch.** Rejected on inbox-noise grounds and on the pragmatic observation that parents want one artifact per booking action, not N. Resolved — no per-lesson emails for Jason or anyone else inside a batch; later changes to any single lesson emit the normal per-lesson events.
- **Per-lesson cancel emails on cancel-remaining.** Rejected on the second pass. The earlier draft kept per-lesson cancel emails because "later changes send per-lesson emails" — but cancel-remaining is itself a batch-level action, not a chain of per-lesson decisions, and the inbox-count argument that justified the one-summary email for `batch_booked` applies to the inverse. One `batch_canceled` with a multi-`VEVENT` `METHOD:CANCEL` `.ics` is the symmetrical choice.
- **Allow multi-pool batches with per-lesson approval.** Rejected for v1. Multi-pool batches would mean `needsApproval` runs once per unique pool in the batch, the summary email has to group by pool, and the approve-all affordance has to be scoped per pool. The complexity cost is real and the use case ("a parent books Egret Park on Tuesdays and Swallows Park on Thursdays in the same submission") is speculative. The batch stays one-pool for v1; if Jason wants mixed later, the schema already supports it — `batch_id` doesn't carry pool, each lesson row does — and the add is scoped to the submit and preview endpoints.
- **Row-locking the batch's lessons with `FOR UPDATE` instead of advisory day locks.** Rejected because the slot engine has to re-check availability against all pending/approved lessons in a day, which means we need to serialize per-day writes system-wide — not per-row. `pg_advisory_xact_lock(hashtext('lesson-day:' + laDate))` is the mechanism single-lesson booking already uses; extending it to batch is a trivial loop. Row locks on the batch's own lessons would protect nothing (the rows don't exist yet) and introduce a different lock domain than single-lesson booking.
- **Writing per-lesson outbox rows that reference `batch_id` AND the lesson id.** Rejected because the dedup key `(lesson_id, event, sequence)` + the pre-send supersede guard already handle per-lesson events for every state change downstream of the batch. The CHECK that exactly one of `lesson_id` / `batch_id` is non-null keeps the two namespaces cleanly separated.
- **Dedicated batch detail page in v1.** Rejected on the second pass. Parents don't need a separate view for "lessons in batch X" — the dashboard already lists their upcoming lessons, and a small "part of a weekly batch" or "part of your Nov 4 batch" label on each lesson card gives the parent the association. The batch summary email also lists everything. If a dashboard filter becomes a felt need, it is a Phase 2 UI add, not a schema change.
- **Store `.ics` method and sequence on the batch outbox row and ignore `payload.lessons`.** Rejected because a batch row's `.ics` has multiple `VEVENT`s, each with its own UID and sequence pulled from the specific lesson. A single `(ics_method, ics_sequence)` pair on the row can't represent that; stuffing it with one of the lessons' values would be arbitrary and would break the paired-nullability invariant. Reading sequences from `payload.lessons` at render time is the simplest working model.
- **A single `booking_batch_members` junction table instead of `lessons.batch_id`.** Rejected because every batch member is already a lesson row, and every lesson belongs to at most one batch. A junction with cardinality `(1, 0..1)` is a column, not a table.

## Rollout

One PR, three phases, each phase its own commit set:

- **Phase 1 — schema, server, email.** Migration (`booking_batches` with the weekly columns, `lessons.batch_id`, outbox alterations). `POST /lessons/batch/preview`, `POST /lessons/batch`. The `batch_booked` outbox event, template, and multi-`VEVENT` `.ics` renderer with the send-time filter. Integration tests. **No UI.**
- **Phase 2 — parent UI.** `/dashboard/book/batch` with the manual + weekly flow and the per-pick preview with inline conflict resolution. Dashboard entry points. A small "part of your <date> batch" label on batch lesson cards; no dedicated batch detail page.
- **Phase 3 — approve-all, coach grouping, cancel-remaining.** `PATCH /coach/lessons/batch/:batchId/approve-pending`, grouping on the coach pending list, `batch_approved` outbox event and template reuse. `DELETE /lessons/batch/:batchId/remaining`, `batch_canceled` outbox event, `METHOD:CANCEL` multi-`VEVENT` `.ics`.

Nothing in phases 1–3 requires a backfill or a destructive migration.

## Consequences

- One new table (`booking_batches`), one new column (`lessons.batch_id`), two added columns on `lesson_email_outbox` (`batch_id` plus `lesson_id` becoming nullable), one replaced constraint (the outbox's UNIQUE becomes two partial unique indexes), three new values in the outbox `event` CHECK (`batch_booked`, `batch_approved`, `batch_canceled`), three new values in the `household_audit_log.action` free-text column (`lesson_batch_booked`, `lesson_batch_approved`, `lesson_batch_canceled_remaining`). One generated Drizzle migration and no backfill — existing per-lesson outbox rows all carry `lesson_id`, so the new CHECK is satisfied automatically.
- Three new parent-facing API endpoints: `POST /lessons/batch/preview`, `POST /lessons/batch`, `DELETE /lessons/batch/:batchId/remaining` (Phase 3). One new coach-facing endpoint: `PATCH /coach/lessons/batch/:batchId/approve-pending` (Phase 3). All Zod-validated via `packages/shared/src/schemas/booking.ts`.
- ADR 027's lesson-change-path list grows by the batch write path (per-lesson sync hooks for each approved batch member), the approve-all path, and the cancel-remaining path. ADR 028's list grows the same way, plus the three new events the sender's render path must handle. The follow-up PR that implements this plan updates both ADRs in one doc commit.
- The parent-facing booking surface in the web app grows a batch flow with a mode toggle (manual / weekly), a per-pick preview with inline conflict resolution, and a small per-card batch label on the dashboard. The single-lesson flow is unchanged and remains the default; the batch path is a new entry.
- The sender's render path gains a batch branch — one new template (shared by `batch_booked`, `batch_approved`, and `batch_canceled` with subject/header variants and `METHOD:REQUEST` vs `METHOD:CANCEL` branching on event), one new `.ics` build helper that composes `VEVENT`s from `payload.lessons[]` after applying the send-time filter. React Email's preview server exercises the new template cross-client in the same way as the single-lesson templates.
- The outbox retention scrub (ADR 028, 30-day payload nullification on terminal rows) applies to batch rows without changes: the payload on a terminal batch row is nulled at the 30-day mark alongside its per-lesson siblings.
- No reminders, no unsubscribe link, no price-lock changes — all deferred (reminders out of scope; unsubscribe inappropriate for transactional email per ADR 028; price lock lives in the payments plan). Archived swimmers behave as in single-lesson booking (lesson rows retain their `swimmer_ids`). Season changes surface through the preview's existing flags (`outside_hours`, `day_closed`) rather than any batch-specific logic.
- The recurring-lessons plan at `docs/plans/recurring-lessons.md` stays **shelved** by this ADR as a reference for the open-ended series shape.
